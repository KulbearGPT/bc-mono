# M13：业务集合排序与双视图 Story 设计提案

> 状态：已由 M13-US-01 冻结为正式功能设计基线；排序 API、数据库查询和 Dashboard 双视图运行时仍待 M13-US-02/03 实现。
>
> 提案日期：2026-08-05

## 1. 产品目标

Dashboard 中凡是以业务对象集合展示的页面，统一提供：

- 多种服务端排序；
- `卡片视图` 与 `表格视图` 两种展示方式；
- 桌面端表格在窄屏下自动转为可读的行式列表，不出现必须横向拖动才能完成核心操作的情况；
- 筛选、排序、分页、详情与操作能力在两种视图中保持一致；
- 共用一套集合工具栏、视图切换器、排序模型、查询状态和稳定游标协议。

首批范围固定为七个现有 Dashboard 页面：

1. 订单；
2. 用户；
3. 陪玩；
4. 服务目录；
5. 服务套餐；
6. 礼物目录；
7. 礼物请求。

返佣、陪玩收益、审计、结算、周报等页面不在首批范围；后续可在相同组件和协议上接入，不为它们另建第二套排序或视图系统。

## 2. 核心产品决议

### 2.1 两种视图，不建立两份业务页面

- 视图值固定为 `CARD` 与 `TABLE`。
- `TABLE` 在宽屏使用语义化表格；窄屏按同一列定义降级为行式列表，因此产品文案可称“表格/列表视图”，但状态值仍只有一个 `TABLE`，避免三套渲染逻辑。
- 两种视图消费同一批 API items、同一权限结果、同一详情 API 与同一 item actions；切换视图不重新请求数据。
- 卡片和表格只决定信息密度与布局，不得改变可见对象范围、字段脱敏、操作权限或业务状态。

### 2.2 排序必须在服务端完成

七个接口目前均为游标分页。禁止仅在浏览器中重排当前页，否则会造成跨页漏项、重复项和错误的全局顺序。

统一查询参数建议为：

```text
sortBy=<资源白名单字段>&sortDirection=asc|desc
```

- 每次只选择一个主排序字段；“多种排序”表示每个页面提供多个排序选项，不表示 P0 支持用户编排多列排序。
- API 对每个资源声明允许的 `sortBy` 白名单及默认方向；未知字段或方向返回 `400 VALIDATION_ERROR`。
- 排序键相同的记录必须追加唯一 ID 作为最终 tie-breaker；时间或其他可空字段统一 `NULLS LAST`。
- 游标必须绑定资源、可信 Guild/scope、筛选条件、`sortBy`、`sortDirection`、主排序值和唯一 ID。排序或筛选变化后旧游标不可复用。
- 客户端不按状态文案、格式化金额或本地时区字符串排序。

### 2.3 查询状态与交互

- 工具栏顺序：筛选条件 → 排序选择 → 方向切换 → 卡片/表格切换 → 清除。
- 改变筛选或排序：清空现有游标，从第一页重新加载，并保留所选视图。
- 改变视图：保留 items、筛选、排序与当前分页位置，不触发 API 请求。
- URL query 保存 `view`、`sortBy`、`sortDirection` 和筛选条件，刷新及复制链接后可恢复；不把游标写成长期书签状态。
- “清除”恢复本页面默认筛选和默认排序，但保留用户当前视图偏好。
- 加载、空、错误、无权限状态均位于视图容器之外，避免同一状态在卡片和表格中重复实现。
- 排序控件显示业务文案，例如“创建时间：最新优先”，不直接暴露字段名。

## 3. 首批排序矩阵

下表是 M13-US-01 冻结的首批业务排序。M13-US-02 实现时必须逐项确认数据库投影、索引与列表响应拥有对应事实；不允许 Dashboard 猜测缺失字段。

| 页面 | 默认排序 | 其他排序选项 |
| --- | --- | --- |
| 订单 | 创建时间：最新优先 | 创建时间：最早优先；最近更新；金额：从高到低；金额：从低到高 |
| 用户 | 创建时间：最新优先 | 创建时间：最早优先；最近更新；显示名称：A–Z；显示名称：Z–A |
| 陪玩 | 创建时间：最新优先 | 创建时间：最早优先；最近更新；显示名称：A–Z；显示名称：Z–A |
| 服务目录 | 创建时间：最新优先 | 创建时间：最早优先；游戏/服务名称：A–Z；客户单价：从高到低；客户单价：从低到高；版本：从新到旧 |
| 服务套餐 | 创建时间：最新优先 | 创建时间：最早优先；套餐名称：A–Z；套餐总价：从高到低；套餐总价：从低到高；版本：从新到旧 |
| 礼物目录 | 创建时间：最新优先 | 创建时间：最早优先；礼物名称：A–Z；价格：从高到低；价格：从低到高；版本：从新到旧 |
| 礼物请求 | 创建时间：最新优先 | 创建时间：最早优先；最近更新；金额：从高到低；金额：从低到高；到期时间：最紧急优先 |

补充约束：

- 名称排序采用数据库中冻结的统一 collation 规则，API 测试固定中英文、大小写、数字和空值样例，不能依赖运行节点默认 locale。
- 金额仅在同一接口合同允许的同币种范围内排序；若未来单页允许多币种，必须先按币种分组或取消金额排序，禁止直接混排不同币种。
- “状态优先级”暂不进入首批排序。若后续需要“待处理优先”，必须由业务合同冻结显式优先级，不能按枚举字母顺序或由前端自定义。
- “最近更新”使用服务端业务记录 `updatedAt`；没有该事实的资源不得以渲染时间、详情加载时间或 `createdAt` 冒充。

## 4. 复用设计

建议建立一个集合页面配置模型，而不是在七个 route 中分别写条件判断：

```ts
type CollectionViewMode = 'CARD' | 'TABLE';
type SortDirection = 'asc' | 'desc';

interface CollectionPageDefinition {
  page: AdminBusinessPageId;
  defaultView: CollectionViewMode;
  defaultSort: { sortBy: string; sortDirection: SortDirection };
  sortOptions: ReadonlyArray<{
    id: string;
    label: string;
    directions: ReadonlyArray<SortDirection>;
  }>;
  tableColumns: ReadonlyArray<ColumnDefinition>;
  renderCard: (item: AdminBusinessItem) => ReactNode;
}
```

建议复用边界：

- `CollectionToolbar`：筛选槽位、排序选择、方向、视图切换、清除；
- `CollectionState`：loading / empty / error / forbidden；
- `CollectionCardGrid`：统一网格、卡片 action 区、详情入口；
- `CollectionTable`：显式列定义、固定操作列、窄屏行式列表；
- `useCollectionQueryState`：URL 状态、默认值、游标重置规则；
- `buildAdminResourceQuery`：只接受页面配置白名单中的排序值；
- 服务端 `ListSortDefinition`：把公开 sort key 映射到受控 SQL 表达式、空值规则和唯一 tie-breaker，禁止把 query 参数直接拼入 SQL。

表格列必须由页面显式配置，不继续依赖首屏 items 动态收集字段；否则不同页或空值会造成列抖动，并可能意外展示新增的内部字段。

## 5. Epic 与 Story 拆分

### EP-M13：业务集合稳定排序与可复用双视图

**用户价值**

运营人员可以按当前任务选择合适顺序，并在高信息密度表格与易扫读卡片之间切换，而不会丢失筛选、分页或操作上下文。

**范围**

为七类 Dashboard 集合建立统一服务端排序、稳定游标、共用工具栏、卡片/表格双视图、URL 状态和响应式列表。

**依赖**

`M4-US-03; M10-US-08`

**Epic 验收**

- 七页均至少有默认排序和三种以上业务排序选择；
- 七页均可在 `CARD` / `TABLE` 间切换，数据、详情与 item actions 一致；
- 排序在跨页、并发新增数据和相同排序键下保持稳定；
- 权限、Guild scope、返佣保密、金额格式与详情读取边界不发生回归；
- 桌面表格与窄屏行式列表可键盘操作并具备可读标签。

### M13-US-01：排序与双视图合同及 RED 基线

**作为** 产品、开发和 QA，**我希望** 七类集合共享明确的排序与视图合同，**从而** 后续实现不会各自解释默认顺序、游标或响应式行为。

**范围**

- 冻结 `sortBy` / `sortDirection` 通用参数、七资源白名单、默认值、空值及 tie-breaker 规则；
- 冻结 `CARD` / `TABLE`、窄屏降级、URL 状态和筛选/排序/分页联动；
- 同步主规格、backlog、OpenAPI、交互映射、验收用例、TODO 与镜像；
- 建立合同 RED 基线。

**依赖**

`M4-US-03; M10-US-08`

**验收标准**

- 七个 operationId 均引用统一参数，但各自只接受本资源白名单；
- 默认排序、标签文案、方向、空值和唯一 tie-breaker 可机械验证；
- 明确仅前端当前页排序、客户端 SQL 字段透传和状态字母排序均不合法；
- 合同 Story 不实现运行时代码或迁移。

**建议估算**：2–3 人日。

### M13-US-02：七类列表 API 的稳定排序与游标

**作为** 运营人员，**我希望** 翻页前后始终遵循所选全局顺序，**从而** 不会因当前页重排而遗漏或重复处理对象。

**范围**

- 为 `listAdminOrders`、`listAdminUsers`、`listAdminPlayers`、`listServiceCatalogVersions`、`listAdminServicePackages`、`listAdminGiftCatalogItems`、`listAdminGiftRequests` 接入统一排序解析器；
- 为每个资源建立受控字段映射、稳定 keyset 查询和必要索引；
- 游标签名绑定排序、筛选、资源、Guild 与可信 scope；
- 保持现有 RBAC、脱敏和默认分页上限。

**依赖**

`M13-US-01`

**验收标准**

- 每个白名单排序均覆盖升/降序、相同键、空值、首尾页和篡改游标；
- 排序或筛选改变后使用旧游标返回 `400`，不会静默解释为新查询；
- 并发插入时不重复返回已经翻过的记录，稳定快照能力不作超出 keyset 合同的承诺；
- SQL 不接受原始列名或方向拼接；Guild/scope 条件在排序和分页之前生效；
- 查询计划与索引证据满足现有 P0 列表数据规模，不引入全表客户端加载。

**建议估算**：5–8 人日。

### M13-US-03：可复用集合工具栏与卡片/表格接入

**作为** 运营人员，**我希望** 七个页面以相同方式排序和切换视图，**从而** 无需每到一个页面重新学习操作。

**范围**

- 实现共用集合配置、工具栏、查询状态、卡片网格、显式列表格和窄屏行式列表；
- 七页接入同一 query state 与 API 排序参数；
- 补齐当前仅有表格的用户、礼物目录、礼物请求卡片；补齐当前仅有卡片的订单、陪玩、服务目录、服务套餐表格；
- 两种视图复用同一详情入口与 item actions。

**依赖**

`M13-US-02`

**验收标准**

- 七页均出现同位置、同文案结构的排序和视图控件；
- 切换视图不发起列表 API 请求，不丢筛选、排序、items、分页或已打开详情；
- 改变排序只发起一次第一页请求，并避免旧请求晚到覆盖新结果；
- 两种视图的对象数量、对象 ID、可见字段等级、详情入口和 action capability 完全一致；
- 表格列显式定义，操作列在两种视图中均可达；窄屏无核心操作被裁切；
- URL 刷新与复制链接恢复视图、排序和筛选；无效 URL 值安全回退默认值。

**建议估算**：6–9 人日。

### M13-US-04：跨页一致性、可访问性与发布验收

**作为** 产品、运营和 QA，**我希望** 在真实数据和不同屏幕下复核排序与双视图，**从而** 发布时不会出现漏项、权限泄露或只能在某种视图操作的问题。

**范围**

- 自动化覆盖七页排序矩阵、游标、URL 恢复、请求竞态、两视图 parity、键盘和窄屏；
- 使用同键、大数据页、归档记录、不同权限和跨 Guild fixture；
- 执行真实 Dashboard 员工会话 UAT。

**依赖**

`M13-US-03`

**验收标准**

- 七页逐项完成默认排序、至少三种排序、升降序、跨页和空状态验证；
- L1–L4 在两种视图看到相同 scope 与 actions，403/404 不泄露对象；
- 375px、768px 和桌面宽度下核心字段、详情和操作可达；
- 键盘可操作排序、方向、视图切换与表格/列表 action，控件有可读名称和选中状态；
- 全量回归、Dashboard production build、类型检查、API/数据库测试和真实员工 UAT 有证据后才可完成。

**建议估算**：3–5 人日。

## 7. 非目标与风险

首批明确不做：

- 用户自定义多列排序、拖拽列、隐藏列或保存多套个人视图；
- 浏览器导出、批量选择、批量修改、无限滚动或虚拟化大表；
- 由前端计算业务优先级、金额、余额、状态或权限；
- 将详情 API 合并进列表快照，或为了表格展示扩大敏感字段；
- 为七页复制七套排序组件、视图状态或 SQL 构造器。

主要风险及约束：

- **游标兼容**：排序合同上线后，旧游标必须明确失效并返回可恢复错误；客户端自动回第一页。
- **索引成本**：不是每个字段组合都适合增加复合索引；合同 Story 先冻结有真实运营价值的有限白名单。
- **名称 collation**：中英文混排必须在数据库与测试中固定规则，不能以开发机结果作为合同。
- **动态表格泄密**：现有动态收集字段的方式需要退役，改为显式列白名单。
- **视图偏好与业务查询耦合**：`view` 只影响渲染，绝不能进入 API 权限或游标签名。
