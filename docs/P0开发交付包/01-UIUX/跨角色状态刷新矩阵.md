# 跨角色状态刷新矩阵（M19）

## 1. 目的与权威规则

本矩阵把每次业务事实变化映射到客户、陪玩、客服 Discord 协同卡和客服工作台，避免只刷新发起操作的一方。M19 不允许 Bot 或 Dashboard 推导业务状态；所有展示均来自统一 API 的最新投影。

- 客户不提交 readiness。订单首次从 `ACCEPTED` 进入 `IN_SERVICE` 前，必须所有当前有效陪玩均已就绪。
- 事务提交与 Outbox 写入必须处于同一原子边界；业务成功但展示失败时重试展示，不回滚或重复业务写入。
- 高频变化原位更新已持久化消息；只有开始招募、服务开始、完成、真正取消等里程碑可新增一次性消息或横幅。
- 每个写操作成功后，所有受影响投影必须由同一订单版本收敛；陈旧版本不得覆盖较新状态。
- 客服工作台采用“写成功后主动失效并重取 + 前台可见时短轮询 + 用户手动刷新”三层策略；不把浏览器缓存当作实时事实。

## 2. 订单状态与四类受众

| 状态/变化 | 客户订单面板 | 陪玩可见信息 | 客服协同卡 | 客服工作台 | 更新方式与失败恢复 |
|---|---|---|---|---|---|
| `DRAFT` 创建、需求/备注/数量变化 | 当前步骤、完整需求、报价、余额与唯一下一步 | 不可见 | 无卡片 | 有权限员工查询时看到最新草稿与版本 | 客户交互成功后编辑原面板；409 立即重取，不覆盖新事实 |
| `DRAFT` → `PENDING_DISPATCH` | 已预留金额、未开始招募或招募入口 | 尚无公开报名信息 | 无卡片；异常时才建任务 | 订单状态、预留、提交时间及时刷新 | 状态、预留和 `PANEL_SYNC` 同事务；Discord 失败由 Outbox 重试 |
| `PENDING_DISPATCH` 开始招募 | 当前轮次、项目缺口、当前报名名单 | 派单卡、数字 Reaction 映射、项目需求 | 仅需人工介入时出现任务 | 轮次、报名数量、招募开始时间 | 首次横幅一次；报名卡与客户面板原位更新 |
| `PENDING_DISPATCH` 报名/撤回 | 按项目列出当前有效报名者 mention | Reaction 即操作反馈，失败时移除不可信新增 Reaction | 已存在任务时同步报名数与最近变化 | 报名列表、项目缺口、更新时间 | API 事实成功后同时刷新公开卡、客户面板与已有客服投影；静默 mention |
| 招募终止进入试音匹配 | 试音名单、语音入口、确认/重新招募 | 报名卡关闭；有效报名陪玩获得试音房访问 | 试音任务、客户、报名人数、语音入口 | 池状态、有效报名、下一步 | 关闭卡、权限和通知均可幂等重试，不自动选择或取消 |
| 部分确认正式陪玩，仍有缺口 | 已确认陪玩、剩余缺口、可继续招募 | 入选者订单访问；未入选者权限收敛 | 当前阵容、剩余缺口、下一步 | 参与人、个人快照、需求填充度 | 参与人事务成功后统一 `PANEL_SYNC`；权限失败重试不回滚阵容 |
| 全部名额满足进入 `ACCEPTED` | 逐名陪玩 readiness、截止时间；客户无 readiness 按钮 | 每位陪玩只看到自己的确认动作及全员进度 | 客服协同卡显示逐人 ✅/⏳、截止时间、订单/试音/服务房入口 | 逐人 readiness、全员是否就绪、截止时间 | 创建一次协同卡，之后每次 `PANEL_SYNC` 原位更新，包括仍处于 `ACCEPTED` 的部分就绪 |
| `ACCEPTED` 部分陪玩就绪/撤销 | 逐名状态即时变化 | 本人动作结果和最新全员进度 | 原位更新逐人状态、待确认名单与剩余时间 | 主动失效订单详情与任务；显示参与人 readiness 而非客户 readiness | 参与人事实与 Outbox 同事务；重复事件按订单版本收敛 |
| readiness 超时且仍为 `ACCEPTED` | 明确“哪些陪玩尚未确认，已转客服” | 未就绪陪玩收到准确提示；不得要求客户确认 | 协同卡加超时警示；唯一客服任务/提醒 | 队列、逾期状态、逐人未就绪名单、等待时长 | 超时任务幂等；提醒原位更新；不自动开始、不捕获 |
| 全员就绪进入 `IN_SERVICE` | 实际开始时间、服务房、求助动作 | 服务开始、自己的项目与预计收益 | 状态、开始时间、参与人和服务房原位更新 | 订单状态、开始时间、自动化与资金仍为预留 | 仅 API 返回 `IN_SERVICE` 后展示开始；里程碑消息至多一次 |
| `IN_SERVICE` 阵容/价格调整 | 最新逐人项目和订单总价；客户确认前必须可见 | 受影响陪玩看到自己的新快照 | 原位更新阵容、价格影响和操作人结果 | 参与人、预留差额、审计与版本 | 金额与预留原子更新；余额不足零写入；所有端重取同一版本 |
| `IN_SERVICE` → `PENDING_CONFIRMATION` | 谁申请完成、最新逐人价格、确认完成主动作 | 等待客户确认；申请人明确已提交 | 当前状态、申请时间、等待客户 | 完成请求、确认截止、任务状态 | 原位更新；超时只建客服任务，不自动完成或扣款 |
| `PENDING_CONFIRMATION` → `COMPLETED` | 捕获结果、消费、感谢与可用评分 | 每位陪玩实际收益结果 | 完成状态、时间、资金结果；无需继续处理的任务收敛 | 订单、捕获、收益、返佣/Adjustment、任务、评分资格 | 状态和资金同事务；完成里程碑一次；展示失败可重试 |
| 取消预览/`CANCELLATION_ASSIST` | 当前不是已取消、资金影响、等待客服 | 不显示虚假终态；必要时提示等待协调 | 原位显示原因、金额边界、任务和建议动作 | 取消预览、任务、预留状态、审批/结案动作 | 预览不改状态；只在 API 返回终态后改变展示 |
| 真正进入 `CANCELLED` | 取消结果、预留释放/退款事实 | 订单访问与操作收敛 | 取消状态、资金结果、处理完成 | 订单、释放/退款、任务、事件时间线 | 流单横幅一次；频道归档单独重试；不得提前显示取消成功 |
| `EXCEPTION` | 明确“状态待核对”、客服已介入和 request_id | 停止正常前进动作，保留必要事实 | 高优先级异常、已知/未知写入结果、恢复入口 | 异常状态、失败 Job、资金保留、审计与可执行动作 | fail-closed；不猜测资金或状态；授权修复后再次统一刷新 |

## 3. 非订单业务刷新覆盖

| 业务 | 必须同步的消费者 | 体验要求 |
|---|---|---|
| 礼物请求、批准、拒绝、过期 | 客户私密结果、接收陪玩、公开庆祝（仅批准）、客服任务/工作台、钱包投影 | 请求只显示预留；批准才广播；拒绝/过期释放后更新余额，不把公开消息失败当作交易失败 |
| 客服任务创建、认领、首响、升级、结案 | 订单频道提醒、客服队列、任务详情、订单详情 | 首响后原提醒收敛；认领不被并发覆盖；L1 个人队列与 L2+ 全局队列均重取 |
| 订单退款与 Adjustment | 客户余额/消费、订单详情、客服工作台、结算与审计投影 | 只追加事实；金额、币种和方向一致；不修改历史交易 |
| 陪玩审批、暂停、标签变更 | 陪玩工作台、未来可报名池、客服目录 | 立即影响新报名资格，不追溯改写既有正式订单；Presence 仅诊断 |
| Bot 配置与频道恢复 | 常驻入口、派单/客服频道、Worker 投递目标、客服配置页 | 版本更新后失效配置缓存；错误目标不丢业务事实；测试投递不创建业务数据 |

## 4. 时效与可观测性验收

- API 写成功后必须在同一响应内返回新版本；Outbox 最迟在正常 Worker 下一轮处理，目标 5 秒内收敛。
- Dashboard 在自身写成功后立即重取；订单/任务详情前台可见时每 5 秒轻量重取，页面隐藏时暂停；恢复可见立即重取。
- Outbox 达最大重试、目标 Discord 消息丢失、版本倒退或客服投影超过 30 秒未收敛时产生结构化告警，包含 `order_id`、`event_type`、`request_id`、目标消费者与最后错误，不记录敏感正文。
- 自动化必须证明：业务与 Outbox 原子性、每个转换的消费者覆盖、Discord 原位更新与重启幂等、Dashboard 陈旧响应隔离、客服逐人 readiness 和超时文案准确。
