v1.0 变更摘要

状态口径
明确“已规划/已契约”不等于“已实现”，本交付包不替代代码、迁移、测试或部署证据。
P0 对标
加入基于公开产品介绍的对标矩阵，并明确比较属于产品推断、不是竞品合同事实。
路线图
新增 08 产品路线图，以 P1-01—P1-06 定义下一阶段必要能力和依赖顺序。
范围隔离
每个 PL 项均写明 P0 排除；微信/邮箱、白标、多租户、连接器、营销/VIP 只在 Nice-to-have 附录保留。
P0 核心
内部 CAT 钱包成为唯一资金事实；L2+ 根据 USD receipt 按固定 1 USD cent = 1 CAT subunit 即时充值，渠道退款后登记非负 CAT 扣款，所有非只读操作进入只追加审计；猫条/CAT 名称、符号和比例不可配置。
招募与终选
客户手动开始和终止无截止候选池；陪玩按需求报名或撤回，客户原子终选正式陪玩。时间流逝、零报名和 Worker 重启均不自动选人、关闭候选池或释放订单预留。
服务开始
客户不提交 readiness；所有当前有效陪玩分别确认本人就绪后才进入 IN_SERVICE，超时只转客服。

共同约束

主题必须遵守
业务事实来源订单、预留、礼物、返佣、收益、审批与权限由统一 API 和 PostgreSQL 保存；Bot 与 Dashboard 不复制业务规则。
资金边界内部 CAT 钱包保存账户、充值、真实余额、预留、消费和退款事实；第三方渠道仅由工作人员在线下核对，系统不读取或写入支付渠道 API。
余额口径availableMinor = ledgerBalanceMinor - reservedMinor；预留是记录合计，不是可手工编辑字段。
权限L1 基础客服、L2 客服主管、L3 运营负责人、L4 管理员/所有者；权限按 L1<L2<L3<L4 累积继承。一般礼物和退款允许达到最低等级的同一人员执行，高额 ≥500000 必须 L4；高额手动结算必须由不同人员复核。保留原因、step-up/MFA 和不可篡改审计，API 是最终授权点。
返佣隐私PROMOTER_FIRST_PURCHASE 与 PLAYER_LIFETIME 互斥；被推荐用户永远不得获知受益关系。
数据删除订单、资金、消费、收益、礼物、返佣、退款与审计不硬删除；使用释放、冲正、禁用、归档或追加更正。
P0 非目标不做下单前公开陪玩目录、优先名单或强指定、预约排班、完整 BI、多 Server/多渠道、原生移动端、白标、多租户、VIP 或营销系统；本单有效报名池内的客户终选属于 P0。
