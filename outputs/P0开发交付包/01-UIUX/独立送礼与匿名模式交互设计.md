# M22 独立送礼与匿名模式交互设计

状态：M22-US-01 合同已冻结；运行时与发布由 M22-US-02 至 M22-US-05 逐步实现，M22-US-06 负责三条入口的非 UI 自动化与隔离测试数据门禁。现有订单内送礼继续保留。

## 1. 入口与最短路径

- 运营在同 Guild 配置专用 `gift_entry_channel_id`。Bot 启动、配置变化或消息丢失时，确保该频道只有一条由 Bot 管理并置顶的送礼常驻消息。
- 常驻 Embed 底部提供“送礼物”“查看猫条”“充值帮助”三个按钮；余额和个人数据只在 ephemeral 中展示。
- 老板点击“送礼物”后依次完成：选择一位陪玩 → 选择礼物 → 核对余额与署名方式 → 确认赠送。
- 公开署名是默认值；老板只在需要时额外点击“匿名赠送”，因此普通路径不增加点击。
- 订单面板原有送礼入口和订单内多陪玩能力继续保留，不强迫老板先创建或查找订单。

## 2. 接收人和礼物选择

- 独立入口只展示统一 API 返回的同 Guild、`PlayerProfile.reviewStatus=ACTIVE` 且存在同 Guild Discord 绑定的陪玩。
- Discord Select 提交 `playerProfileId`；API 在最终事务中重新校验陪玩资格，并从 PlayerProfile 派生真实 `receiverId`。Bot、Dashboard 和请求体不得接受任意 `receiverId`。
- 单次独立送礼只选一位陪玩和一种礼物。需要送给多人时分别提交，避免金额与匿名意图混淆。
- 礼物 Select 只展示 ACTIVE、CAT 计价的目录版本；最终确认必须带预期目录版本和价格，价格变化时回到核对页重新确认。

## 3. 余额与充值续接

- 选择完成后先调用只读 affordability API。可用余额由 API 在同一内部钱包口径返回，Discord 不自行计算。
- 余额充足时显示礼物、陪玩、署名方式、将预留金额与“确认赠送”。确认后才原子创建 GiftRequest、ACTIVE FundReservation 和 GIFT_REVIEW 客服任务。
- 余额不足时仍保留已选陪玩、礼物和匿名意图，只显示余额不足、差额、充值帮助、刷新余额和返回；不创建礼物、预留或客服任务。
- 充值由客服线下核对 receipt 并写入内部 CAT 钱包。老板点击“刷新余额”后重新读取目录、陪玩资格和余额；任一事实变化都要求重新确认。
- continuation 使用绑定 Guild、老板和选择事实的签名短期 token，不依赖 Bot 进程内 Map；过期、篡改或换用户失败关闭。

## 4. 匿名边界

- `PUBLIC`：面向陪玩和礼物播报频道显示安全的老板展示名。
- `ANONYMOUS`：面向陪玩、公共礼物播报和其他非员工投影统一显示“匿名老板”，不得包含 Discord mention、用户名、用户 ID、头像 URL 或可反推身份的订单/私密频道信息。
- 匿名只影响面向陪玩与公共频道的展示。客服、资金、风控和审计仍使用真实 `sender_id`；老板本人可在私密历史中看到自己的真实送礼记录。
- 匿名事实在请求创建时冻结；批准、重试、删卡恢复和模板变化不得把匿名改回公开。
- 礼物播报模板在匿名模式下由服务端使用安全 sender label 渲染，客户端不得传入替代 sender 文本。

## 5. 持久化与来源

- GiftRequest 增加不可变 `guildId`、`origin=ORDER|STANDALONE` 与 `senderVisibility=PUBLIC|ANONYMOUS`。
- `ORDER` 来源保留 `orderId` 和订单参与明细；`STANDALONE` 来源的 `orderId/orderParticipantId` 均为空。
- StaffTask 的 `orderId` 已允许为空；独立送礼任务只绑定 GiftRequest，并在内部 context snapshot 保存 Guild、真实 sender/receiver、目录和预留事实。
- 新增 GuildGiftEntryMessage 保存每个 Guild 的频道、消息和渲染版本，用于启动恢复、配置迁移与消息丢失重建；它不保存余额、选择或业务规则。

## 6. 客服指令边界

客服辅助采用模式 B，并由独立 Story（M22-US-04）实现：客服是最终确认人，可在专用权限和二次验证通过后直接预留老板余额；该能力不扩大普通 `gift.request`。

- 客服在老板本人发送且明确表达送礼请求的消息上，使用消息右键菜单“协助此老板送礼”。Bot 验证消息作者不是 Bot 且属于当前 Guild，再把客户 Discord 用户、频道和消息 ID 作为客户授权消息证据提交；不保存消息正文。
- API 只从可信客服 Actor Context 与同 Guild Discord 绑定解析客服和余额所有者。请求体不接受 `senderId`、`receiverId`、客服等级或权限；跨 Guild、非 ACTIVE 客户、未审批客服和无 `gift.assist` 权限均失败关闭。
- 低点击路径为：消息右键菜单 → 选择陪玩 → 选择礼物 → 可选切换匿名 → 最终确认。最终按钮打开一个 Modal，同时收集必填原因和客服本人六位 TOTP，不要求老板再点一次。
- 客服最终确认人不是老板代理登录。TOTP 只证明当前客服本人执行高风险动作；客户意图由授权消息的 Guild、频道、消息和作者证据与客服必填原因共同留痕。任何投影不得保存或回显 TOTP。
- API 创建十分钟有效、最多五次失败、只能消费一次的辅助 challenge，并绑定客服、`permissions_version`、Guild、老板及授权消息。Bot 重启后的选择状态使用签名 token，不依赖进程内 Map。
- affordability 仍是只读；余额不足显示差额和充值帮助且零写入。最终事务锁定 challenge 和老板钱包，重新校验权限、客户、陪玩、目录、价格和余额，再原子创建礼物、ACTIVE 预留、客服任务、预留事件和审计。错误 TOTP、过期、篡改、权限变化、重复提交或并发超支均不创建预留。
- GiftRequest 标记 `initiatorMode=STAFF_ASSISTED`，关联真实客服与辅助 challenge；sender 仍是老板，FundReservation 仍属于老板，资金/客服/风控/审计同时记录客服执行者。匿名展示边界与老板自助送礼完全相同。
