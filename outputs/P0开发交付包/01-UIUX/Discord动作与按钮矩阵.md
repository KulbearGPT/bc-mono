# Discord 动作与按钮矩阵（M20）

## 1. 目标与事实边界

- 每个客户可操作的非终态订单都必须保留清晰的“取消订单”入口；取消后的处理结果仍由统一业务 API 根据当前状态、资金和权限决定。`COMPLETED`、`CANCELLED` 为终态，不再显示取消入口。
- API 返回可信 `availableActions`，至少包含动作键、可执行性、角色、危险级别和不可执行原因。Bot、Worker 与 Dashboard 不得仅凭状态、自报角色或消息所在频道推导可用动作。
- 客户主面板只放老板可执行动作；陪玩工作台只放当前陪玩可执行动作；客服协同卡只放客服可执行动作。共享只读事实可以复用，跨角色写按钮不得混在同一常驻卡上。
- 同一动作在四步下单、常驻订单卡、招募与试音、生命周期、服务中心和错误恢复中使用同一动作键与标签词库。

## 2. 客户订单状态动作矩阵

| 状态 | 客户主动作 | 取消入口 | 资金与状态结果 | 辅助动作 |
| --- | --- | --- | --- | --- |
| `DRAFT` | 按当前步骤继续下单 | `取消订单` | API 取消草稿；没有预留则不产生释放 | `查看已选服务`、`刷新最新状态`、`联系猫舍前台` |
| `PENDING_DISPATCH` | `结束报名，进入试音` 或等待报名 | `取消订单` | API 确认取消后释放原预留 | `填写订单备注`、`刷新最新状态`、`联系猫舍前台` |
| `ACCEPTED` | 查看陪玩准备进度 | `申请取消订单` | 进入客服审核，不伪装为已取消 | `刷新最新状态`、`联系猫舍前台` |
| `IN_SERVICE` | 等待陪玩提交完成或联系客服 | `申请取消订单` | 进入客服审核；资金保持可信现状 | `赠送礼物`、`刷新最新状态`、`联系猫舍前台` |
| `PENDING_CONFIRMATION` | `老板：确认服务完成` | `申请取消订单` | 进入客服审核；未确认前不显示已退款或已释放 | `刷新最新状态`、`联系猫舍前台` |
| `CANCELLATION_ASSIST` | `查看取消处理进度` | 保留取消分区并明确“客服处理中”，不重复创建请求 | 保持当前预留或捕获事实，等待客服决定 | `刷新最新状态`、`联系猫舍前台` |
| `EXCEPTION` | `查看异常处理进度` | `申请取消订单` | 创建或复用客服任务；不得由 Bot 猜测终态 | `刷新最新状态`、`联系猫舍前台` |
| `COMPLETED` | `再次下单` | 不显示 | 只显示 API 确认的完成与消费结果 | `查看消费记录`、`联系猫舍前台` |
| `CANCELLED` | `再次下单` | 不显示 | 只显示 API 确认的取消与释放/退款结果 | `查看消费记录`、`联系猫舍前台` |

## 3. 角色动作分离

| 视图 | 允许出现的写动作 | 不得出现 |
| --- | --- | --- |
| 客户主面板 | 继续下单、备注、招募/试音、选择陪玩、老板完成确认、礼物、取消、客服 | 陪玩就绪、陪玩申请完成、客服认领/结案 |
| 陪玩工作台 | 报名/撤回、`陪玩：我已准备好`、`陪玩：提交服务完成`、打开当前订单、刷新 | 老板取消、老板完成确认、其他陪玩的就绪动作 |
| 客服协同卡 | 打开任务、认领、首响、升级、结案、刷新 | 客户提交、陪玩就绪、替客户确认完成 |

候选确认页同样属于客户主面板：即使已有报名陪玩，也必须保留取消、刷新和客服入口。任何点击后都重新读取 API 返回的 `availableActions`；陈旧按钮应返回清楚的冲突反馈并刷新原卡。

## 4. 首次使用可理解的按钮词库

| 旧标签 | 统一新标签 |
| --- | --- |
| 进入 | 查看这个游戏 |
| 查看 | 查看套餐内容 |
| 单点加入 | 加入这个单点服务 |
| 采用套餐 | 把此套餐加入订单 |
| ＋ 添加其他游戏或单点 | 继续添加游戏或服务 |
| 查看清单 / 查看已点清单 | 查看已选服务 |
| 席位偏好 | 填写这个席位的需求 |
| 下一步 · 确认订单 | 核对订单与总价 |
| 确认提交订单 | 提交订单并预留猫条 |
| 终止招募 | 结束报名，进入试音 |
| 重新开始招募 | 再发起一轮报名 |
| 确认选择 | 确认这些陪玩 |
| 返回重选 | 修改陪玩名单 |
| 我已就绪 | 陪玩：我已准备好 |
| 申请完成 | 陪玩：提交服务完成 |
| 确认完成 | 老板：确认服务完成 |
| 当前订单 | 打开当前订单 |
| 刷新订单 / 刷新 | 刷新最新状态 / 刷新当前页面 |
| 我要申诉 | 联系猫舍前台；只有真实争议表单使用“提交申诉” |

按钮必须使用“动词 + 对象/结果”，不能只写“进入”“查看”“确认”“刷新”等脱离上下文的单词。

## 5. 组件布局规则

- 一屏最多一个 Primary；多个目录卡同时出现时使用 Secondary，只有本屏唯一推进动作使用 Primary。
- 每行通常不超过三个按钮；不得把五个互不相关动作挤在同一行。
- 主流程、导航/刷新/客服、危险动作分行；危险动作单独成行，并与不可逆主动作保持距离。
- 禁用按钮只在解释当前阻断原因确有价值时显示；没有目标对象的“当前订单”、空分页和纯占位按钮直接省略。
- 分页同时提供上一页和下一页，并保留稳定查询上下文；首页/末页省略对应不可用按钮。
- Modal 提交和危险确认后使用原位更新或 ephemeral 结果，不额外制造一张角色错误的常驻卡。

## 6. 收敛与验收

- 所有生产 action renderer 必须消费统一动作视图模型；旧测试专用 dropdown/dispatch renderer 无生产调用时删除或明确隔离。
- 自动化按状态 × 角色表驱动，覆盖按钮存在性、唯一 Primary、每行数量、custom ID 可达、取消预览/确认、过期版本和权限拒绝。
- 真实 Guild UAT 至少覆盖老板首次下单、已有报名的试音页、陪玩工作台、服务完成、取消审核及终态，桌面与手机均需验证按钮含义和换行。
