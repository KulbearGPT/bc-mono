1. 文档摘要

本文档是 P0 当前主规格，不表示产品已实现。Sapphire Bot 与 Dashboard 都是统一业务 API 的适配器客户端，不保存或重复实现业务规则；自有系统负责内部 CAT 账户、追加式账本、人工充值、资金预留、礼物、消费、退款、返佣、陪玩收益、权限、审计和运营视图。外部支付渠道只作为 USD receipt 的人工证据来源，不是运行时余额或交易依赖。

核心原则：Discord 频道和 Dashboard 只承载交互。统一 API 负责业务状态、权限、幂等和并发；订单在提交时预留、完成时捕获，礼物在请求时预留、批准时捕获。资金摘要只使用 ledgerBalanceMinor、reservedMinor、availableMinor，其中 availableMinor = ledgerBalanceMinor - reservedMinor。

1.1 原型要证明什么

  • 普通用户无需学习大量斜杠命令，也能在 3–4 个主要步骤内完成下单。
  • 系统能创建仅相关人员可见的订单频道，并使用一条可持续更新的操作面板完成订单生命周期。
  • 符合内部审批、Guild 与需求标签的陪玩可在客户手动开启的无时限招募中进入候选池；客户手动终止后在选秀阶段原子选择一个或多个正式陪玩。
  • 客户不提交 readiness，只读查看逐名进度；只有所有当前有效陪玩均确认就绪才进入服务中，任一陪玩超时都转客服。
  • 礼物请求创建时就预留资金；客服只核对品类、目标和沟通结果，有权限的 L2–L4 批准时由 API 捕获既有预留，不人工计算余额。
  • PROMOTER_FIRST_PURCHASE 和 PLAYER_LIFETIME 两种互斥返佣计划可被准确结算、冲正和审计，且对被推荐用户严格保密。
  • 下单、取消和完成由 API 按合同推进；候选池开始/终止与正式陪玩终选由客户明确操作，关键阶段可请求客服接管、暂停、转派或提交审批。
  • 统一运营工作台提供候选池与正式参与人视图、四级细粒度 RBAC/审计、自动运营记账轨迹和八项最小指标。

1.2 推荐技术取舍

业务形态

模块化单体。一个代码库，按用户、订单、派单、礼物、返佣拆模块。

运行进程

统一业务 API、Dashboard 前端与 Sapphire Discord Bot 分工运行；只有 API 访问 PostgreSQL，Bot 和 Dashboard 都通过 API 完成业务。

资金边界

内部追加式 CAT 账本是唯一余额事实源；统一 API 原子维护预留、捕获、释放、业务退款和线下渠道退款扣减。

2. 原型范围

2.1 必须实现（P0）

模块最小能力
公共入口固定消息提供“创建订单”和“我的服务中心”两个按钮；不要求用户记忆命令。
内部资金账户Discord 用户首次注册、进入服务中心或下单时由 API 幂等取得或创建唯一 CAT 账户；不绑定外部支付账号。
人工充值完成近期 step-up 的 L2+ 在 Dashboard 按 receipt 录入 USD cents、付款方式、交易号、付款时间、原因、备注和可选图片/PDF；验证通过后按固定比例追加 CAT CREDIT。
服务目录与计价配置游戏、服务、区服、计价单位、最低单位数、客户单价和陪玩结算单价；订单提交时保存价格版本与快照。
私密订单点击后创建用户、Bot、管理员可见的私密频道；生成唯一订单与常驻面板。
订单操作首版仅支持即时单；提交前一次确认需求、价格、资金摘要和取消规则；提交时预留，全体有效陪玩就绪后服务，用户确认完成时捕获。
陪玩准入与报名陪玩必须审核为 ACTIVE、属于同一 Guild 且匹配需求标签；不设置“在线 / 可接单”业务状态，Presence 只作诊断。
候选池选秀Bot 只提供“开始招募”和“终止招募”；客户不设置等待分钟数，招募不会按时间自动结束。报名或撤回后，客户订单 Embed 原位实时列出当前报名陪玩的 Discord mention；客户手动终止后，所有有效报名者进入选秀语音房，由客户原子选择正式陪玩。
终选与陪玩就绪终选成功后展示正式陪玩资料摘要和下一步；客户只读查看逐名进度，所有当前有效陪玩分别确认本人就绪后才自动进入 IN_SERVICE。
陪玩工作台提供独立必备界面，展示资格、可报名候选池、本人报名、正式订单、需求详情、无截止招募状态、收益摘要和下一步动作；候选池不显示倒计时。
礼物系统用户从符合条件的订单面板选择礼物，接收陪玩由订单锁定；请求时立即预留，客服核对品类、目标和沟通结果，L2–L4 批准时由 API 捕获预留，然后记账与播报。
客服处理集中展示送礼、订单协助、取消协助和异常任务；送礼强制人工确认，其他流程默认自动但可被客服接管。
消费历史统一展示订单与礼物消费记录、时间、金额、对象和状态。
陪玩收益订单完成或人工结案后，按订单保存的结算价生成待确认收益；支持确认、人工标记支付和退款冲正，不自动提现。
返佣计划PROMOTER_FIRST_PURCHASE（老板带新）与 PLAYER_LIFETIME 互斥；支持绑定、结算、冲正、受益人自查和被推荐人保密。
统一运营工作台整合任务、订单、用户、陪玩、派单、预留、消费、退款、收益、礼物、返佣、审批和审计；按四级权限决定数据范围与操作。
Bot 基础配置L3/L4 通过 /bot-config 管理频道路由、通知、时限和开关；L4 额外管理 Role 映射。所有配置由统一 API 校验、版本化和审计。
运营记账与指标余额快照、预留、消费、退款、陪玩收益、返佣与冲正自动进入同一业务时间线，并提供八项 P0 最小运营指标。

2.2 启动前最优先六项

稳定 ID必须锁定的 P0 能力验收焦点
PL-01结构化需求与完整确认：游戏、服务、区服、时长、标签、备注、价格、可用余额和取消规则在提交前一次展示。用户不需跨页拼接信息；确认后仍由 API 重新校验。
PL-02原子资金预留：摘要统一显示内部账本余额、预留金额和可用余额；availableMinor = ledgerBalanceMinor - reservedMinor。订单和礼物并发请求不能超支，reservedMinor 来自有效预留合计。
PL-03候选池透明与终选结果：显示招募/选秀阶段、当前有效报名者 Discord mention 与客户动作，不显示截止时间；终选后显示正式陪玩资料摘要和用户下一步。报名进度和名单实时可见，终选由客户决定且多名人选原子提交。
PL-04陪玩工作台：独立显示资格、可报名候选池、本人报名、正式订单、需求详情、无截止招募状态、收益摘要和下一步动作；候选池不显示倒计时。陪玩无需设置在线或可接单状态，也无需依赖管理员查询日常信息。
PL-05全体陪玩就绪再开始：客户不提交 readiness；所有当前有效陪玩分别确认本人就绪后才自动进入服务中，超时转客服。不存在部分陪玩就绪就开始计费的正常路径。
PL-06取消影响预览：执行取消或申请客服前，显示可自动处理性、预计释放/退款金额、处理方式和时效。预览不构成承诺；执行结果仍由 API 按最新版本原子校验。

2.3 下一阶段与 Nice to Have

下一阶段统一编号为 P1-01 至 P1-06：陪玩档案展示与试音/审核材料、保证指定陪玩、预约与排班、更完整的经营/对账/导出、多服务器或多渠道接入、移动端运营和通知中心。P0 即时单统一使用开放报名候选池，不保留优先名单或独占首轮。Nice to Have 包括额外登录、白标/自定义域名、多租户/复杂代理层级、大范围连接器、营销自动化、VIP、优惠券和活动系统。

2.4 明确非目标

  • 不自动读取或操作 Stripe、PayPal、信用卡收单方等外部支付平台；不自动验证 receipt 真伪。
  • 不保存银行卡、CVV、支付密码或外部平台 Secret；receipt 图片/PDF 仅进入私有文件存储。
  • 内部 CAT 账本不可手工覆盖；充值、消费、退款和纠错均通过只追加流水表达，FundReservation 负责冻结层。
  • 平台内名称、符号和比例固定为猫条 / CAT，1 USD = 10 CAT 且 1 USD cent = 1 CAT subunit；不得配置第二账本或动态汇率。
  • 客户、客服、目录、审批、陪玩收益、返佣、周报和结算业务事实显示 CAT；充值付款证据与陪玩线下实际结算可辅助显示 USD，但不形成第二账本。
  • 不做多级返佣、公开通用推荐计划、自动提现、税务处理、代理层级或返佣资金发放。
  • P0 不做预约单、排班日历、陪玩试音、保证指定陪玩、智能推荐算法、动态竞价或跨服务器派单；即时单支持最多九个项目需求、开放报名候选池和客户原子终选多位陪玩。
  • 不做优惠券、VIP、会员等级、独立客服工单产品、复杂客服 SLA 或完整财务报表；轻量完单评价和明确同意后的五星公开播报属于当前 P0。
  • 不保证在 Bot 离线期间继续提供 Discord 交互；后台数据与系统任务仍应可保存。
Prototype 限制：第一版只支持单个 Discord Server、单币种、即时订单以及每名用户最多一个未结束订单频道；同一订单可包含不限数量的项目需求和陪玩，但不支持预约排班。超出范围由管理员后台人工处理。

3. 功能流程（给非技术人员看的白话版）

这一节只解释“谁在什么时候做什么，以及最后会看到什么”。系统内部状态、数据库和 API 细节从下一节开始。

整体原则：能自动完成的事情默认自动完成；用户随时可以点“联系客服”；遇到余额、权限、退款或争议等异常时，系统自动把事情交给客服。送礼因为涉及对象、品类和公开播报，必须先由客服核对，并由有审批权限的主管或管理员批准。

3.1 用户第一次使用

用户在公共频道先幂等“注册为玩家”，随后可创建订单或打开服务中心。API 根据可信 Discord Actor Context 取得内部 CAT 账户；用户可以看到 CAT 账本余额、预留、可用、进行中订单和消费历史，以及自己作为受益人的脱敏返佣/收益摘要，不需要学习斜杠命令或绑定外部支付账号。

3.2 下单

点击创建订单→进入私密频道→填写结构化需求→一次确认需求/价格/余额/取消→预留并进入候选池

用户点击“创建订单”后，Bot 建立一个只有用户、Bot 和客服能看到的私密订单频道。首版只支持“尽快开始”的即时单；用户可逐条添加游戏、服务、区服、时长和需要人数不同的需求项，并填写标签和备注。提交前页面一次展示完整需求清单、服务端报价、CAT 账本余额、预留、可用余额和取消规则。确认提交时 API 以 CAT subunits 原子创建订单预留，不立即扣款；无法自动处理时交给客服。

3.3 招募、终选和服务完成

订单提交后，API 为每条需求项建立独立待匹配名额；Bot 只让客户开始招募，不收集等待分钟数；Bot 通知已经审核为 ACTIVE、同 Guild 且对应项目和标签匹配的陪玩。每轮在派单频道只发布一张报名卡，按稳定需求顺序展示最多九个项目并对应 1️⃣ 至 9️⃣ Reaction；陪玩添加数字 Reaction 报名对应项目，移除该 Reaction 撤回该项目。超过九个项目时 API 拒绝开始招募，不拆分、不截断。陪玩可同时报名多个订单，报名与进入选秀语音房均不占用活动订单槽位。招募保持 COLLECTING，不会自然截止；每次报名或撤回都经统一 API 写入事实并触发同一客户订单 Embed 原位刷新，以 <@discordUserId> 形式列出当前有效报名者，且通过 allowed_mentions.parse=[] 避免重复通知。仅客户手动终止招募后进入不限时选秀，客服频道收到含语音链接的任务通知；客户原子确认一个或多个正式陪玩，最终选择时才校验并占用活动订单槽位。全部名额满足后订单才进入已接单。客户不提交 readiness，只读查看逐名进度；所有当前有效陪玩分别确认本人就绪后才自动进入服务中。任一陪玩可申请完成，由用户确认；确认时 API 捕获订单预留，然后按参与明细分别记录陪玩收益及符合条件的返佣。30 分钟未确认则转客服，不自动完成或捕获。

3.4 取消订单

用户在执行取消或申请客服前，先看到该状态能否自动处理、预计释放或退款金额、处理方式和时效。草稿无资金动作；已提交但未捕获的订单取消时释放预留。已开始、争议或需部分结案时，预留保持不变并转客服；结案决议原子捕获应消费部分、释放剩余部分，并明确陪玩收益。预览只是预计，最终由 API 按最新状态、版本和幂等键执行。

3.5 送礼物

从订单或独立入口选择陪玩与礼物→预留资金并创建任务→L1+ 核对→有权限的 L2/L3/L4 批准→捕获与记账→公开或匿名播报
  1. 订单内送礼继续保留：用户可从符合条件的订单选择一个或多个有效陪玩明细，客户端只提交 participantIds。独立送礼入口允许用户随时从 API 返回的同 Guild ACTIVE 陪玩中选择一位，并只提交 playerProfileId。两条路径都由 API 推导真实接收人，不接受任意 receiverId。余额不足时只显示差额、充值指引、刷新和返回且零业务写入。
  2. 用户确认时，API 立即创建礼物预留和客服任务，防止并发礼物或订单超支；此时尚未捕获消费。
  3. 客服卡片显示礼物、目标、订单或独立入口来源、真实用户联系方式、可用语音频道链接、预留状态、有效期和可执行动作；匿名模式不向内部客服隐藏付款人。
  4. L1 或更高等级客服核对品类、目标和沟通结果，然后提交审批；客服不人工计算余额，L1 不能直接捕获。
  5. 系统按金额把请求交给有权限的 L2/L3/L4。批准时 API 校验预留、版本和幂等键，捕获已有预留；本地预留模式下还会重新读取内部账本余额并原子校验。
  6. 捕获成功后，自有系统保存礼物和消费事实，并通过 Outbox 播报。拒绝、过期或撤回则释放预留；播报失败只重试消息，不重复捕获。
语音链接规则：候选池进入选秀阶段后，Worker 必须以订单为幂等键创建或恢复一个 user_limit=0 的私密语音频道并写入 selection_voice_channel_id。选秀期间客户、全部有效报名者和已配置的 L1-L4 客服 Role 可查看并连接，客服 Role 可管理频道。终选后 Worker 另建仅客户、入选陪玩和客服可见的 service-{订单号} 正式服务房，先移动客户、再移动入选陪玩，并将该频道写入 voice_channel_id；未入选者撤权并移出。旧 Selection 房进入只退不进状态，最后一人退出后由 Bot 自动删除。客户 Ticket 提示正式服务房已经创建，客服协调卡同时保留选秀协调入口并增加服务房入口；重试或重启不得重复建房或重复通知。

3.6 返佣计划与保密

PROMOTER_FIRST_PURCHASE 业务上称“老板带新”，通过邀请码或管理员手工绑定，按一次性固定额或首笔符合条件净消费比例结算，一次结算后永久结束。PLAYER_LIFETIME 表示陪玩带来的客人，按配置对长期符合条件的净订单和/或净礼物消费返点。一名被推荐用户只能有一个有效来源，两计划互斥，普通用户不可修改。只有受益人能在自己的“返佣/收益”中看到记录，来源用户默认脱敏；被推荐用户在用户 API、Discord、错误、导出和通知中永远不会得知受益人、关系类型、比例、金额或状态。

3.7 客服如何介入

必须人工确认

所有送礼请求。L1 可认领、联系用户和提交审批；最终批准/拒绝由 L2–L4 按金额和权限执行。

默认自动，可人工接管

下单、派单、取消和完成。用户主动求助、超时、规则命中或自动化失败时生成客服任务；客服可暂停自动化、转派或提交审批。

客服任务与订单状态分开保存。客服接管不会篡改历史记录；批准、拒绝、退款、转派等操作都会留下操作人、时间和原因。

3.8 客服和管理员如何使用 Dashboard

客服登录后台后先看到自己的待办和已认领任务。L1 可以查授权范围订单、联系用户、写内部备注、核对送礼信息并提交建议，但看不到系统密钥，也不能执行充值、渠道退款扣款、Adjustment、封禁用户或修改规则。完成近期 step-up 的 L2+ 可按 USD cents receipt 登记 CAT 充值，并在余额充足时登记渠道退款扣款；运营负责人可追加关联原流水的 Adjustment 并处理用户状态和业务配置；管理员/所有者只在人员权限、安全配置或紧急停机等系统级操作时介入。订单人工恢复继续使用原权限范围：L1 仅限已认领任务，L2+ 限同 Guild，不要求订单进入过招募；未捕获非终态订单可更正或清空订单及席位备注、增删改派陪玩，更正必须保留只追加事件和审计并同步 Bot 面板，终态或已捕获订单失败关闭。

L1 核对并提交→系统判断权限和金额→L2/L3/L4 按规则审批→执行操作→写入审计并通知

3.9 Bot 和 Dashboard 为什么会得到相同结果

用户在 Discord 点击“取消订单”，或客服在 Dashboard 点击同一操作时，两个界面都会把请求交给同一套业务 API。API 根据操作者、订单状态、金额和权限决定自动取消、生成审批或拒绝操作，再把结果返回给界面。因此规则只维护一份，Bot 重启、Dashboard 改版或新增其他客户端都不会改变业务结果。

3.10 陪玩如何获得收益

陪玩通过独立工作台查看审核资格、可报名候选池、本人报名、正式订单、需求详情、就绪/完成倒计时、收益摘要和下一步动作；工作台不提供在线或可接单业务开关。每个上架服务同时配置客户单价和陪玩结算单价，客户终选时保存个人分成快照；订单捕获完成或人工结案后生成收益。运营可确认并人工标记已支付，退款时追加 Adjustment 冲正；原收益不允许覆盖或删除。

5.4 高风险操作规则

  • 权限由 API 根据累积后的 permission_code、操作者级别、对象状态和金额共同判断；高等级自动拥有所有低等级执行权限，前端隐藏按钮不算权限控制。
  • Discord Role 映射只能授予不高于内部审批结果的有效权限；请求级别高于已批准级别时，API 始终取较低值。
  • Prototype 默认 L2 送礼审批上限为 200000 CAT subunits、退款上限为 50000 CAT subunits；超出后创建 approval_request 并升级给 L3。
  • 单笔送礼或退款达到 500000 CAT subunits 时最低要求 L4；L4 可以直接发起并执行，不要求另一名人员复核。
  • 所有非只读操作（Dashboard、Discord 用户/陪玩、Bot、Webhook 与 Job）无论成功、失败或被拒绝，都必须写入审计日志；成功业务变更与审计头、逐对象变更明细必须在同一数据库事务提交。
  • 扣款、退款、封禁、规则变更、权限变更和集成变更还必须填写原因、预览影响并二次确认。
  • 财务流水、订单事件和审计日志只追加不覆盖；纠错只能创建冲正或更正记录。
  • 服务目录双价格、部分退款和陪玩收益确认/冲正属于财务相关操作，必须保存订单快照、原因和操作人。
  • L3/L4 执行敏感操作前必须完成近期二次验证；prototype 默认有效期 15 分钟。

5.5 私密订单频道权限

  • @everyone：拒绝查看频道。
  • 下单用户：允许查看、发消息、读取历史、使用组件；不得管理频道。
  • 候选与正式陪玩：选秀阶段全部有效报名者可进入语音房；终选后只有正式陪玩继续保留订单访问，未入选者权限被撤销；取消、移除或归档后继续收敛。
  • L1–L4 客服工作人员：按任务或管理范围查看并可管理或删除频道；L1 只能协助和提交审批，不能绕过 Dashboard/API 权限执行高风险动作。
  • Bot：允许管理频道、消息与权限覆盖。

5.6 客服处理频道权限

  • 仅客服、管理员和 Bot 可查看；用户与陪玩不能进入。
  • L1 可以认领、打开订单频道、加入有权限的语音频道、私聊用户、写备注和提交审批。
  • 扣款、退款、拒绝、取消和关闭任务必须跳转 Dashboard 或调用同一业务 API，由 L2–L4 按权限和金额执行。

  1. 系统检查用户是否已有未结束订单；若有，提供“进入现有订单”按钮。
  2. 创建订单草稿和私密频道，发送并置顶一条常驻面板。
  3. 用户在四步点菜式订单向导中按游戏选择套餐或单点，第二步可通过单字段 Modal 填写整单需求备注，第三步可逐席位编辑时长与席位偏好；每次交互后由 Bot 更新同一条 Components V2 消息。“优先陪玩” User Select 不再出现在当前 P0 向导；优先名单、独占首轮和自动回退语义均已退役，提交后统一创建开放报名候选池。
  4. 业务服务根据目录中的计价单位、客户单价和最低单位数估价；订单同时保存目录版本、客户单价和陪玩结算单价快照。
  5. 确认页一次展示游戏、服务、区服、时长、标签、备注、价格、内部账本余额、预留金额、可用余额和取消规则。
  6. 用户点击“确认并提交”；统一 API 再次读取账户事实，以业务来源、幂等键和版本原子创建 FundReservation，成功后进入 PENDING_DISPATCH 并等待客户开始招募；此时不立即捕获消费。
  7. 用户点击“联系客服”、风控/规则命中或自动提交失败时，系统创建客服任务；否则不增加人工审批等待。

6.3 候选池报名与客户选秀

订单提交后由客户点击“开始招募”创建开放报名候选池；Bot 与 API 不收集等待分钟数，也不安排自然截止任务。旧 auto_dispatch_enabled、dispatch.manual、定向派单、定时收口和自动续轮不再控制 P0 业务流程。客户订单 Embed 在报名或撤回后原位实时列出当前报名陪玩的 Discord mention。仅客户点击“终止招募”后进入不限时选秀并通知客服，客户原子选择正式陪玩；零报名或客户对本轮候选均不满意时，可由客户主动重新开始招募或取消订单。

  1. 根据订单的游戏、服务和区服标签筛选陪玩。
  2. 报名者必须同时满足：准入状态为 ACTIVE、同 Guild 且标签匹配；Discord Presence、旧 availability 和现有活动订单不阻止报名。
  3. 客户点击“开始招募”后，Bot 在集中招募频道发送一张带需求 Reaction 映射的报名卡；报名或撤回均通过 API 幂等写入，并原位刷新客户订单 Embed 中的候选 mention。
  4. 报名不创建正式参与人且不占活动订单槽位；客户手动终止招募后，所有有效候选进入不限时选秀。
  5. 客户按候选池版本原子终选一名或多名正式陪玩；API 在同一并发控制边界重验资格、需求名额与活动槽位，成功后才创建参与明细、授权订单频道并展示逐名 readiness。
  6. 仅订单客户点击“终止招募”时，统一 API 才按池版本将本轮候选池幂等从 COLLECTING 迁移到 SELECTION；时间流逝、Worker 重启或旧截止任务均不得触发该迁移。任何情况都不自动续轮；零报名或客户对本轮候选均不满意时，客户可显式重新开始招募。API 必须按池版本原子结束旧池、将仍有效报名标记为未入选并创建新池，保持订单及原预留不变；客户也可取消并释放原预留或联系客服。进入选秀后不设置选择超时，只在客服频道创建可跟进任务，不自动选人或扣款。

6.4 服务与完成

  1. 终选成功后开始 10 分钟陪玩就绪宽限期；客户只读查看逐名进度，所有当前有效陪玩在本人面板确认自己的 readiness。
  2. 只有所有当前有效 order_participants.ready_at 均存在时，API 才自动将订单从 ACCEPTED 迁移到 IN_SERVICE 并记录实际开始时间。
  3. 任何一方未在宽限期内就绪都创建 PLAYER_START_LATE 客服任务，订单保持 ACCEPTED，不自动扣罚、捕获或释放。
  4. 陪玩完成后点击“申请完成”，等待用户确认。
  5. 用户点击“确认完成”后，API 先以预留的稳定幂等键捕获订单金额；捕获成功才完成订单，并生成消费事实、陪玩收益和符合计划的返佣。
  6. 用户 30 分钟未确认时创建 COMPLETION_REVIEW 任务；订单保持待确认，由客服决定完成、恢复服务或进入争议，不自动完成。
  7. 订单完成或取消后，相关订单文字频道、选秀语音房和正式服务语音房进入终态清理；默认且最长保留 1 小时，先将文字频道锁为只读，再完整回填仍可从 Discord 读取的频道消息并成功追加 transcript，随后删除语音频道，最后删除文字频道。

6.5 取消订单

  • 待招募/候选池/选秀：用户可取消；API 释放订单预留，成功后关闭候选池，不把未捕获金额描述为退款。
  • 已终选及以后：P0 不允许用户直接自动取消，系统先展示影响预览并创建 CANCELLATION_ASSIST 客服任务；争议期预留保持。
  • 用户主动点击“联系客服”、释放/捕获失败或状态变更时也创建客服任务；订单不得在资金结果未确认前显示为已取消或已完成。

6.6 赠送礼物与播报

  1. 用户可以从符合条件的订单面板或独立礼物频道的常驻消息点击“赠送礼物”。订单路径从有效 participantIds 推导接收人；独立路径从同 Guild ACTIVE playerProfileId 推导唯一接收人；两者均不接受客户端提交 receiverId。
  2. API 返回三项资金摘要。若礼物价格超过 availableMinor，客户端禁用确认，显示差额和充值入口。
  3. 确认时 API 对去重后的有效订单陪玩明细逐人创建 gift_request、PENDING FundReservation 和 GIFT_REVIEW 客服任务，并在同一事务中全部提交或全部回滚。卡片显示礼物、对应陪玩、来源订单、用户联系方式、语音链接、预留状态、有效期和可执行动作。
  4. L1 或更高等级客服认领任务，通过语音或私聊核对品类、目标和沟通结果，然后将任务标记为“已核对，待审批”；L1 无权捕获或最终拒绝，任何客服都不人工计算余额。
  5. 系统按最低级别路由：L2 可批准 ≤ 200000 CAT subunits，L3 处理更高但低于 500000 CAT subunits 的金额，≥ 500000 CAT subunits 由 L4 直接执行；任何更高级别也可执行低级别动作。
  6. 批准后 API 校验有效预留、版本和幂等键，捕获已有预留；本地预留模式在捕获前重新读取内部账本余额。成功后创建消费事实；拒绝、过期或撤回后释放预留。
  7. Outbox 任务向配置的礼物频道播报，并更新播报状态；失败只重试播报，不重复扣款。
  8. 礼物是否计入返佣由配置决定，prototype 默认计入符合条件的净消费。

6.7 返佣计划

  • PROMOTER_FIRST_PURCHASE（老板带新）通过邀请码或管理员手工绑定，按固定额或首笔符合条件净消费百分比结算一次，结算后永久结束。
  • PLAYER_LIFETIME 适用于陪玩带来的客人，按配置对长期符合条件的净订单和/或净礼物消费返点。
  • 一名被推荐用户只能有一个有效来源，两计划互斥；绑定、改绑和冲正必须审计，普通用户不可修改。
  • 退款或结案追加 Adjustment 冲正，原返佣记录不覆盖或删除；Adjustment 金额为非负绝对值，由 type 表达方向。
  • 推广者/陪玩可查自己收益，来源用户默认脱敏。L1 默认不可看受益人和金额，L2 仅按任务有限查看，L3/L4 可绑定、纠错、确认和审计。
  • 被推荐用户的用户 API、Discord、错误、导出和通知不得暴露受益人、关系类型、比例、金额或状态。

6.8 客服接管

  1. 客服任务由用户主动求助、业务规则、派单/readiness/完成超时、用户/陪玩爽约、服务中断、资金或自动化错误以及强制礼物复核触发。
  2. 客服在集中处理频道点击“认领”，避免多人重复处理。
  3. L1 负责核对和提交；L2–L4 根据任务类型、金额与权限执行批准、拒绝、暂停/恢复自动化、转派、预留释放/捕获重试或关闭任务。
  4. 每个动作写入审计日志，并更新订单频道和客服卡片；客服任务状态不替代订单状态。

Embed订单面板、派单卡片、客服任务卡片、礼物播报。金额、状态和订单编号需醒目；不放支付敏感信息。
级联选择规则：游戏、服务等关联选项不能在一个打开中的 Modal 内动态联动。用户每次提交消息组件后，Bot 调用统一 API 取得下一组可选项并编辑原订单消息；提交 Modal 后，也必须先处理该次提交，再以消息或新的 Modal 展示后续内容。

实现时以 Discord 官方的 组件参考与Modal 组件指南为准。Sapphire 通过当前版本的 discord.js Builder 创建这些组件；锁定依赖版本并在测试服务器验证，不能仅假设任意 14.x 都具备相同 Modal 组件能力。

10. API 草案

统一前缀 /api/v1。Discord Bot 与 Dashboard 调用同一套业务接口和应用用例：Bot 使用受限服务账号并代表当前 Discord 操作者，Dashboard 使用 Discord OAuth2 登录后的后台会话。所有写接口接受 Idempotency-Key，响应包含 request_id；API 在每个入口执行相同的对象归属、权限码、金额、状态与审批策略。

复用原则：/admin 表示“需要工作人员权限”，不表示“只能由 Dashboard 调用”。Discord 客服卡片上的认领、核对、审批等按钮也可调用这些接口，但必须携带真实点击者上下文，并通过同一套 RBAC 和审计。

11.2 Sapphire 适配规则

  • 按钮、Select 和 Modal 统一由 InteractionHandler 路由；custom_id 只保存对象类型、ID 和动作，不塞业务数据。
  • 管理员命令先通过 Precondition 粗筛；按钮和 Modal 将真实点击者的 Discord User/Guild/Interaction ID 交给 API，随后由 API 解析内部身份并校验对象级权限。
  • Bot API Client 使用独立服务 Token；只有通过该服务身份的请求才能携带 Actor Header。Role ID 只允许提交到 Role Sync 用例，不作为普通业务接口的权限参数。
  • Listener 负责 Gateway 与框架事件；业务服务通过 Outbox/事件请求 Bot 更新消息，避免在 Listener 内写交易逻辑。
  • 部署入口和修复命令使用 Command；普通用户不需要面对大型斜杠菜单。
  • Sapphire container 只注册 API Client、logger、config 和 Discord renderer，禁止作为可随意写入的全局业务状态。

11.3 幂等与并发

  • Discord 的 interaction.id 作为交互幂等依据，重复提交返回首次结果。
  • 预留创建、捕获、释放和退款必须携带稳定 Idempotency-Key 与预期版本，重试不生成新键。
  • 报名按陪玩与需求幂等；客户终选锁订单和全部参与明细，只有版本、资格、Guild、标签与活动槽仍有效时才一次提交正式参与人。
  • 返佣使用来源唯一约束，避免事件重放产生重复记录。
  • 客服认领使用条件更新：仅当任务为 OPEN 时第一位客服可以认领。
  • 礼物批准使用固定 CAT 捕获幂等键 debit:gift:{giftRequestId}:v1 捕获本地预留；重复点击不重复 WalletEntry、消费或播报任务。
  • 面板更新失败不回滚已经成功的业务事务；通过 Outbox 重试同步 Discord 展示。

12. 错误处理与恢复

场景用户提示系统处理
数据库或审计暂不可用“资金操作暂时不可用，请稍后重试。”失败关闭并回滚全部业务变化；记录 request_id，可按原幂等键安全重试。
可用余额不足展示内部账本余额、预留金额、可用余额、差额和充值入口。订单保持草稿；礼物禁用确认；都不创建预留。
预留版本冲突“资金状态已经变化，请刷新后重试。”不重复扣款；返回最新余额与版本。
创建频道失败Ephemeral 告知并提供重试。订单不进入可提交状态；后台记录失败原因。
多个陪玩同时报名每人看到自己的报名结果。数据库唯一约束保证每人每需求只有一条有效报名；所有合格报名者都可进入候选池。
候选池无人报名显示无人报名并让客户选择重新开始招募、取消或联系客服。保持原预留且不自动续轮；重新招募只创建新候选池，取消时释放。
客服任务被同时认领后点击者看到“该任务已由其他客服认领”。数据库条件更新保证唯一认领人。
礼物预留过期或版本变化“送礼预留已失效，请刷新后重新发起。”不捕获、不播报；原预留幂等释放，客服不手工改余额。
陪玩就绪超时客户和陪玩看到“已转客服核对”，并只列未确认陪玩。保持 ACCEPTED 和订单预留，创建 PLAYER_START_LATE；不以部分陪玩就绪开始或计费。
没有语音频道链接卡片显示“未检测到订单语音”。保留私聊用户和进入订单文字频道的入口，不阻断审核。
送礼请求长时间无人认领用户看到“等待客服确认”。10 分钟后提醒值班客服，不自动批准或拒绝。
Dashboard 会话失效“登录已过期，请重新登录。”返回 401，撤销前端缓存，不执行原操作。
Bot 服务身份或 Actor Context 无效“暂时无法验证操作身份，请稍后重试。”返回 401；不执行业务动作，记录 client_id、interaction_id 和拒绝原因。
Discord Role 尚未同步“工作人员权限正在同步，请稍后重试。”返回 STAFF_ACCOUNT_REQUIRED；不根据请求中自报 Role 临时放行。

Role 被移除或降级“权限已更新，请重新登录。”立即应用较低级别、递增 permissions_version、撤销 Dashboard 会话并拒绝旧权限请求。
后台越权操作“当前级别无权执行；需要 L2/L3/L4。”返回 403，不返回敏感对象内容，并记录被拒绝的权限码。
需要二次验证弹出重新验证流程。返回 428；验证成功后使用原 Idempotency-Key 重放一次。
审批已过期或数据已变化“原审批已失效，请刷新并重新提交。”不得沿用旧批准结果；创建新申请并关联旧记录。

退款失败“取消处理中，客服将跟进。”订单进入 EXCEPTION，不提前标记 CANCELLED。

用户 30 分钟未确认完成双方看到“等待客服核对”。创建 COMPLETION_REVIEW；不自动完成、不生成陪玩收益。

人工结案金额不合法“退款或收益金额超出订单范围。”返回 422；不写结案、不追加钱包流水、不创建收益。
面板消息被删除管理员触发修复。根据订单数据库重建面板并更新 message_id。

13.3 L1 日常处理流程

  1. 从“我的任务”认领一项，详情抽屉展示必要的脱敏用户信息、订单时间线和 Discord 频道入口。
  2. 通过语音或私聊核对，将结论写入内部备注；内部备注不发送给用户。
  3. 若不涉及高风险操作，L1 可完成“已联系、资料已补充、升级异常”等非破坏性动作。
  4. 若需要退款、已接单取消、爽约/中断结案、收益调整、封禁或配置变更，L1 只能提交建议，填写原因码、建议退款、建议收益和证据说明。
  5. 任务进入“等待 L2/L3/L4”状态，L1 可查看进度但不能重复执行或修改审批内容。

13.4 高风险操作流程

选择动作→API 检查权限/金额/对象状态→预览影响并填写原因→二次验证或升级审批→幂等执行→审计与通知
  • Dashboard Dialog 必须显示用户、陪玩、订单、动作、客户退款、陪玩收益、资金去向和不可逆影响，不使用模糊的“确定吗”。Dashboard Dialog 是网页后台组件，不等同于 Discord Modal，也不受 Discord 的五组件和纵向布局限制。
  • 超权限或超金额时不显示伪成功，而是返回审批编号、所需级别和等待状态。
  • 审批人打开请求时重新读取对象和余额；数据变化后原审批失效，必须重新提交。
  • 重复点击、网络重试或多标签页执行同一操作时使用同一 Idempotency-Key，最多执行一次。
  • 完成后同时更新 Dashboard、Discord 订单面板和相关客服任务。

13.5 权限在界面中的表现

  • 无页面查看权限：导航隐藏，直接访问 URL 返回 403 页面。
  • 可查看但不可执行：显示禁用按钮和原因，例如“需要 L2”或“超过 50000 CAT subunits 退款上限”，并提供“提交审批”。
  • 敏感字段按级别脱敏；Receipt 存储凭据、完整支付账号和原始签名不返回到前端。
  • 角色或权限被修改时立即撤销旧会话；下一次 API 调用不能继续沿用缓存权限。
  • 检测到 L3/L4 Discord Role 时显示“待确认级别”和来源 Role；确认前不展示高级操作。Role 被移除后不允许继续保留旧级别按钮。
  • 所有金额显示币种和最小单位换算结果；时间同时显示业务时区和相对等待时长。

14.3 /bot-config 基础配置面板

/bot-config 是 Guild 内 L3/L4 使用的管理命令，返回仅操作者可见的 ephemeral 配置消息。L3 可管理公共入口、订单分类、派单、陪玩工作台、礼物核对/播报、客服任务、运营告警、提醒时限和功能开关；L4 累积继承这些能力，并可管理陪玩及 L1–L4 Discord Role 映射。

  1. Command 从 Discord Interaction 解析 Guild 和操作者，调用统一 API 获取当前配置、版本与权限。
  2. 频道使用 Channel Select，身份组使用 Role Select，固定选项使用 String Select，数字和模板文本使用 Modal。
  3. 选择新值后先调用 validateBotConfigChange，显示旧值、新值和权限/类型检查；校验通过时 API 签发绑定操作者、Guild、版本、规范化变更和原因的短期 validationToken。
  4. 只有点击“确认应用”才携带 validationToken 调用 updateBotConfig；缺失、过期或内容不匹配时 API 拒绝，不能绕过预览直接保存。
  5. API 使用 expectedVersion 防止并发覆盖，保存前后值、原因、真实 staff actor 和时间；成功后立即刷新对应 Guild 缓存，使下一次派单、播报和功能开关判断使用新版本，Bot 重启后也从 API 重新加载。
程序边界：建议使用 commands/admin/bot-config.ts、interaction-handlers/bot-config/、presenters/bot-config-presenter.ts 和既有 Business API Client。Bot 不保存配置权限或业务规则；custom_id 只携带操作类型与短期会话 ID。Bot Token、支付密钥、数据库连接、游戏/价格、礼物目录和返佣规则不允许从 Discord 修改。

14.4 基础安全

  • 生产、测试使用不同 Discord App、数据库与 Receipt 私有存储目录；P0 不需要支付渠道沙箱账号。
  • 数据库每日备份；至少验证一次恢复流程。
  • Dashboard 使用 Discord OAuth2 登录，并要求存在有效的本地 staff_accounts；L1/L2 可由 Role 同步创建，L3/L4 需确认。Discord Server 角色不能单独授予后台权限。
  • Bot 只能通过统一 API 访问业务数据；API 仅对有效 Bot 服务身份接受 Actor Header，并从数据库重新解析真实用户和权限。
  • 启动和 guildMemberUpdate 会对账 Role；L1/L2 可自动生效，首次 L3/L4 必须由现有 L4 确认，降级和撤权立即生效。
  • L3/L4 必须启用 MFA；敏感操作还需 15 分钟内的 step-up 验证。
  • 会话使用 HttpOnly、Secure、SameSite Cookie；禁止把访问令牌存入 localStorage；写操作校验 CSRF。
  • 角色修改、人员离职、异常登录和所有者操作可立即撤销全部会话。
  • 如存在获批准的非资金 Webhook，必须验签并限制时间窗口，防止重放。
  • Bot Token、数据库密码和 Receipt 存储凭据不进入仓库或前端。

15.2 Discord 端手工 E2E

  • 新用户完成绑定，并只能看到自己的余额和历史。
  • 用户创建私密频道，非相关普通成员无法查看。
  • 用户只能从启用且双价格完整的目录创建即时单；余额不足时不能派单。
  • 订单提交后即使目录改价，订单金额和陪玩结算仍使用原版本快照。
  • ACTIVE、同 Guild 且标签匹配的陪玩可报名；Presence、旧 availability 和其他报名或活动订单不阻止报名；PENDING_REVIEW/PAUSED/SUSPENDED 不能报名。
  • 多名陪玩可并发报名同一需求；客户终选多名时要么全部成功，要么零写入。
  • 选秀阶段客户、全部报名者和客服可进入不限人数语音房；终选后未入选者权限被撤销。
  • 订单按合法顺序开始、申请完成、确认完成。
  • 接单后任一有效陪玩未在就绪宽限期内确认、或用户 15 分钟未出现时只创建客服任务，不自动开始计费、退款、扣罚、捕获或生成收益。
  • 陪玩申请完成后用户 30 分钟未确认时进入客服核对，不自动完成或生成收益。
  • 客服结案必须同时填写原因码、退款、陪玩收益和说明；超范围金额被拒绝且不产生部分写入。
  • 用户提交礼物后不会立即扣款，客服处理频道会出现完整审核卡片。
  • 两名客服同时认领时只有一人成功；非客服无法操作审核按钮。
  • 有语音链接时客服可进入；无链接时卡片明确显示并可私聊用户。
  • 有权限的 L2–L4 批准后礼物只扣款一次，播报失败后重试不重复扣款。
  • 礼物接收人始终由请求中的有效 participantIds 经订单陪玩明细推导；API 去重且不接受 receiver_id，任一明细失效时整批零写入。
  • 用户主动求助、已接单取消和自动化失败都能创建客服任务。
  • L1 可以核对并提交审批，但直接调用送礼批准、退款、封禁和配置接口均返回 403。
  • L2 可以批准 200000 CAT subunits 以内礼物和 50000 CAT subunits 以内退款，超额请求返回 APPROVAL_PENDING。
  • 达到 500000 CAT subunits 的送礼或退款最低要求 L4；L4 可直接发起并执行，同一人员操作仍须填写原因、完成二次验证并留下审计。
  • L4 修改工作人员角色后，被修改账号的旧 Dashboard 会话立即失效。
  • 同一张未接单订单分别通过 Discord 按钮和 Dashboard 执行取消时，均调用同一用例并得到相同状态、退款规则和审计结构。
  • 伪造 Actor Header、Discord Role ID、staff_id 或 level 不能取得权限；只有有效 Bot 服务身份或 Dashboard 会话可建立操作者上下文。
  • 增加 L1/L2 Role 后自动获得对应内部级别；首次增加 L3/L4 Role 只产生待确认升级，现有 L4 批准后才生效。
  • 移除或降低 Discord Role 后旧会话立即失效，后续 Bot 和 Dashboard 请求都按较低内部级别判断。
  • 任何级别都找不到硬删除财务/审计记录的 UI 或 API。
  • 完成符合条件的净消费后，老板带新最多生成一次 PROMOTER_FIRST_PURCHASE，陪玩来源按配置生成 PLAYER_LIFETIME；重复事件不重复生成。
  • 自己推荐自己、相同账号互荐或首笔符合条件消费后绑定推荐关系均被拒绝。
  • 正常完成生成一条 PENDING 陪玩收益；部分/全额退款按结案记录创建收益冲正，原记录保持不变。
  • 删除面板后管理员可从后台重建。

17. Prototype 验收标准

17.1 用户体验

  • 用户从公共入口开始，无需输入命令即可创建订单。
  • 已绑定用户从点击入口到提交有效订单，主要操作不超过 4 个阶段。
  • 正式服务频道仅客户、已终选的正式陪玩、Bot 和员工可见；未入选报名者的权限必须最终收敛。
  • 订单面板始终显示最新状态、金额、需求和当前可用动作。
  • 个人余额、消费和返佣仅以私密/ephemeral 方式展示。

17.2 订单与派单

  • 字段不完整、余额不足或扣款失败时，订单不会进入待派单。
  • 只有双价格完整且已上架的服务可下单；订单保存目录版本、客户价和陪玩结算价快照。
  • Prototype 只接受即时单，不接受未来预约时间。
  • 报名陪玩必须 ACTIVE、同 Guild 且标签匹配；Discord Presence、旧 availability 和活跃订单不影响报名。
  • 并发报名可产生多名候选；客户终选时原子校验全部人选和需求容量。
  • 选秀开始后全部有效报名者进入不限人数语音房；终选后未入选者权限最终收敛。
  • 订单只能按定义的状态机迁移；越权或非法操作被拒绝并记录。
  • 待派单取消时，预留释放成功后才能进入已取消；未捕获资金不调用退款。
  • 用户求助、已接单取消和自动化异常都会生成可认领的客服任务。
  • 开始宽限、用户爽约和完成确认超时只创建客服任务，不自动退款、扣罚、完成或结算。
  • 人工结案必须原子地写入原因、退款、陪玩收益、订单事件和审计；任何一步失败都不产生半完成结果。

17.3 礼物、客服、消费与返佣

  • 每个送礼请求都会先进入客服处理频道，未经有权限的 L2–L4 按金额规则批准，不会捕获内部钱包预留或追加扣款流水。
  • 客服卡片显示用户、目标陪玩、礼物、金额、余额、订单以及语音链接或无语音提示。
  • 有权限的审批人批准时 API 校验并捕获请求创建时的原预留；每个礼物请求最多捕获一次并生成一条消费记录，客服不手工重算余额。
  • 礼物扣款成功后即使播报失败，也不会要求用户再次付款。
  • 订单和礼物消费均可在用户消费历史中分页查询。
  • 每个被推荐用户最多一个有效来源且两计划互斥；老板带新按配置的一次性固定额或首笔净消费比例结算，陪玩来源按配置对长期净消费返点。
  • 同一消费来源不会重复生成返佣；退款会产生可审计的冲正。
  • 礼物可送给关联订单的有效陪玩，或通过独立入口送给 API 返回的同 Guild ACTIVE 陪玩；客户端不能指定任意接收人。
  • 推荐关系拒绝自荐、重复账号及首笔符合条件消费后绑定。
  • 订单完成或人工结案生成陪玩收益；退款只通过冲正调整，原收益不可修改或删除。

17.4 Dashboard 与权限

  • L1–L4 登录后看到与角色匹配的导航、数据范围、按钮和金额阈值。
  • L1 可以完成查询、认领、联系、备注和提交审批，但无法直接扣款、退款、取消已接单订单、封禁、改配置或删除。
  • API 在任何入口都执行相同的权限码、scope、金额和对象状态检查；前端隐藏按钮不是唯一防线。
  • Bot 与 Dashboard 复用同一业务 API 和应用用例；同一操作者对同一对象执行同一动作时，状态迁移、金额规则、审批和审计结果一致。
  • Bot 业务请求具有可验证的服务身份和真实 Actor Context；客户端提交的 actor_id、level 或 Role ID 不能直接改变授权结果。
  • Discord Role 映射可在 Dashboard 查看；L1/L2 自动生效，首次 L3/L4 等待现有 L4 确认，Role 降级/移除立即撤权并撤销会话。
  • L2 超过 200000 CAT subunits 送礼或 50000 CAT subunits 退款时得到审批编号；不会执行半成功交易。
  • 达到 500000 CAT subunits 的操作最低要求 L4；L4 可以直接执行，不强制独立申请人与批准人。
  • 角色变更立即撤销旧会话；L3/L4 敏感操作要求近期二次验证。
  • /bot-config 仅返回 ephemeral 配置消息；L3 可修改运营字段，L4 继承并可修改 Role 映射；所有修改先预览校验，再按版本确认应用并写不可删除审计。
  • 财务和审计数据只有冲正、禁用、归档或追加更正，没有任何硬删除路径。

17.5 运维与安全

  • 常见异常可从管理端查看并重试，不需要直接修改数据库。
  • 支付 Webhook 与渠道回调入口保持退役；获批的非资金外部事件需验签、幂等并写入审计，关键管理员操作均可追溯。
  • 每条 Bot/Dashboard 写操作审计均能追溯 client_id、actor_source、真实操作者和可选 interaction_id。
  • 日志不含 Bot Token、Receipt 存储凭据、文件正文或支付敏感数据。
  • 测试环境完成一次数据库备份恢复和 Bot 重启恢复演练。
  • 所有 P0 E2E 场景通过，且没有阻断目录计价、下单、扣款、接单、结案、收益或权限隔离的缺陷。

频道保留Bot 对订单频道消息创建、编辑和删除事件实时追加 transcript；订单进入 COMPLETED 或 CANCELLED 后按 channel_archive_after_completion_minutes 保留，允许配置 0–60 分钟，默认且最长保留 1 小时（配置为 0 时可立即执行）。CHANNEL_ARCHIVE Worker 必须先将文字频道锁为只读，再分页读取并完整回填当时仍可见的全部文字消息；所有 transcript 追加成功后依次删除选秀语音房、正式服务语音房和订单文字频道；任一步失败都保留可重试 Job。Worker 周期扫描终态订单，为遗漏任务或历史僵尸频道补建幂等清理任务。
币种与时区内部 canonical 币种固定 CAT；充值付款证据固定 USD，业务展示时区由服务器配置。

19. Railway Sandbox 店内试运营合同

定位：本节定义尚待实现和外部验收的店内试运营约束，不代表 Railway 已部署、真实 Discord UAT 已通过或产品已达到生产发布条件。

19.1 环境与资金边界

  • 业务环境只允许 SANDBOX 或 PRODUCTION；两者都使用内部 CAT 钱包，不配置资金 Adapter、Provider、支付 Webhook 或外部账户绑定。
  • 所有内部金额使用 CAT subunits；充值付款证据固定为 USD cents 并按 1 USD cent = 1 CAT subunit 入账，不建立第二账本。
  • 统一 API 在同一资金锁内从 WalletEntry 和有效 FundReservation 计算 ledgerBalanceMinor、reservedMinor 与 availableMinor；Bot 和 Dashboard 不自行计算或写入。
  • Sandbox 使用隔离 PostgreSQL、测试 Guild 和合成身份；不得使用生产凭证、真实个人数据或真实付款。

19.2 测试充值与退款

  • 不提供目标余额覆盖或 funding provision。完成近期 step-up 的 L2+ 使用合成 USD receipt 登记 TopUp，系统原子追加 TopUp、CAT CREDIT 和审计。
  • 渠道退款完成后由 L2+ 登记 CAT DEBIT，只能扣除未预留可用余额；业务退款追加 CAT CREDIT；Adjustment 最低 L3 且关联原 WalletEntry。
  • 重复 receipt、幂等重放、余额不足、审计失败或并发冲突必须零部分写入；附件可选、私有且只保存允许的元数据。

19.3 Railway 拓扑与阶段门禁

  • 目标拓扑为同源 Web/API/Dashboard、Worker、Sapphire Bot 三个应用 Service 和 Railway PostgreSQL；只有 Web 暴露公网，Bot 与 Worker 走私网。
  • 店内试运营从 CORE_ORDER 开始，第一波门禁通过后才进入 CORE_ORDER_AND_GIFTS；OFF 表示不施加 Pilot 功能限制。客户端只按 API capability 展示入口，不从 Discord Role 或本地配置推导授权。
  • 内部保留 L1–L4 累积权限模型，四级 Discord Role 都可建立映射；Role 只是信号，内部审批与 permissions_version 才是授权事实。
  • 部署、数据库恢复和真实 Discord 试跑是外部门禁；没有可复核证据时保持未通过。任何资金不一致、跨 Guild/跨用户泄露、越权、重复扣款或不可恢复迁移都立即停止试运营并回滚到上一阶段。

M9 现行补充：Discord 自助入驻与 CAT 内部账本

  • 新人入口频道始终可见，Bot 维护一条常驻消息，提供“注册为玩家”和“申请成为陪玩”两个中文按钮。

  • Discord 产品角色只控制产品可见性，不构成员工授权事实。角色写入失败保留重试任务，Bot 启动对账最终收敛。

  • 业务标签新增、改名和启停要求 catalog.manage 权限、CSRF、幂等与审计，但不属于需要近期 MFA step-up 的敏感操作。
  • 新服务项目、陪玩批准和礼物目录不得手工输入标签代码；Dashboard 只展示并提交已启用标签的稳定 ID。停用标签继续保留历史引用，但不能用于新建或替换版本。
  • 陪玩支持的游戏、服务种类和语言使用直观复选多选；批准后具备权限的员工可再次编辑，API 以完整集合替换并保留审计。
  • 服务目录和礼物目录的现有项目提供编辑入口并回填当前值；保存时创建替代版本，不原地改写历史版本。
  • 服务目录和礼物目录的新增、编辑与启停要求对应管理权限、CSRF、幂等、版本控制和审计，但不要求 MFA 近期 step-up。
  • 已配置的玩家入口频道维护唯一常驻消息，提供注册、申请陪玩和“开始找陪玩”按钮；客户点击下单后由 Bot 创建私密订单频道并调用统一 API 创建订单。重复点击先校验既有频道：频道仍存在时返回原频道；频道已被客服删除时复用新建的私密频道，通过统一 API 原子替换频道与面板映射并恢复订单，不改变订单状态、预留或其他业务事实。
  • 服务项目选择一个游戏、一个服务种类及可选地区；陪玩批准可多选游戏、服务种类和语言；礼物版本选择一个礼物分类。
  • 服务目录配置客户单价与默认陪玩分成比例，不再把统一陪玩结算金额作为业务规则。运营可为每位陪玩、每个服务项目设置百分比分成或每计费单位固定金额，个人规则优先。
  • 订单提交时固化客户价格与默认分成；客户终选正式陪玩时解析并固化每位陪玩的最终单位收益和总收益。之后修改目录或个人规则均不得追溯历史订单。
  • 服务与礼物目录提供“删除”入口，但其领域语义固定为归档：退役活动版本并从默认目录隐藏，不执行物理删除，不改变任何历史订单、礼物请求或金额快照。

M10 订单多陪玩与多接收人礼物补充合同

本节取代本文所有“唯一陪玩”、“客户参与 readiness”、“礼物固定单一接收人”及订单级单一陪玩收益描述。

  • 订单包含一个可分页的陪玩明细集合，不设业务人数上限；Dashboard 使用搜索、分页和逐项写入，不将 Discord 单个 Select 的平台限制当作业务上限。
  • 客户草稿中的“想找什么”使用订单需求项表达，与“最终由谁服务”的陪玩明细严格分离。每条需求项独立绑定服务目录版本、计费数量和所需人数；当前 P0 不接受优先陪玩名单，也不得在客户终选前生成陪玩明细。
  • 套餐模板只是订单需求购物篮的版本化生成器，不是另一种订单或合并后的陪玩人数。套餐的每个默认席位原子展开为一条独立 OrderRequirement，例如“三角洲护航”可默认生成两个技术陪玩席位；客户可把其中一个席位改成娱乐陪玩并填写“技术要求不高、会聊天”等备注，其他席位不受影响。
  • 完整保持套餐默认构成时订单标记为 PACKAGE_DEFAULT，可使用套餐版本配置的默认总价；修改、增加或移除任一席位后立即标记为 CUSTOMIZED，由统一 API 按最终有效需求重新报价。Bot 和 Dashboard 不计算套餐价、改单价、折扣或陪玩收益。
  • 应用套餐必须在单一事务内移除草稿原有需求、展开全部默认席位、追加需求事件并更新订单套餐来源；任一目录版本失效、版本冲突或写入失败时零变更。提交后的候选报名必须绑定具体需求席位，客户终选覆盖全部所需席位后订单才可进入 ACCEPTED。
  • 按游戏点菜式下单与单游戏套餐（M10-US-09）：客户必须先选择游戏，统一 API 再只返回该游戏可用的服务项目和套餐；Bot 只渲染 API 返回的范围，不自行混合、猜测或缓存跨游戏选项。
  • 第二步游戏菜单必须提供“填写需求备注”按钮，打开仅一个可选文本字段的 Discord Modal。该备注属于整单需求，与第三步的逐席位偏好分开；提交必须携带订单期望版本并调用统一 API，成功后回到原游戏菜单并显示已保存内容，过期版本不得覆盖新事实。
  • 一个稳定套餐只属于一个游戏。套餐的 gameCode 与 gameName 由 API 根据全部席位引用的服务目录版本派生并固化，不接受客户端自报；所有席位必须同游戏，新版本也必须保持稳定套餐的游戏归属，混合游戏整次拒绝且零写入。
  • 套餐席位可以改项目，但替换项目必须与该需求席位原有游戏相同；跨游戏不得直接改写既有席位。客户可返回游戏选择，以另一游戏的新单点需求继续加菜；同一订单可按游戏分组包含多游戏需求。上述替换约束与新增语义均由 API 校验，不能只依赖 Discord 过滤。
  • “单独加陪玩”在草稿阶段表示新增一条服务需求席位，而不是提前指定某个陪玩身份；具体陪玩仍由提交后的候选池报名与客户终选产生。Bot 可用 Components V2 的 Section 附件按钮展示套餐，以 String Select 展示该游戏的单点项目。
  • 任何套餐席位的新增、修改或移除都使订单进入 CUSTOMIZED，套餐调价归零，并由 API 按最终有效目录单价重新派生订单总价；客户端不得沿用套餐优惠或自行计算差价。
  • 套餐由 Dashboard 运营端维护，不硬编码在 Bot。L3+ 可把一个或多个有效服务目录版本组成不可变套餐版本，保存名称、说明及逐席位默认偏好；套餐总价只能由 API 按各席位服务目录单价乘以计费单位数汇总并固化，Dashboard 仅实时展示且不得直接输入或提交套餐总价。新版本先为草稿，发布时原子退役同套餐旧启用版本，已生成订单继续引用历史版本。退役不删除历史套餐、席位或订单来源。
  • Discord 通过可恢复的逐条编排器添加、修改、移除和分页展示需求项。提交时至少有一条有效需求；API 按每条目录单价乘计费数量再乘所需人数派生报价和预留，Bot 不计算金额。
  • 每条需求项产生所需人数个终选席位。报名必须绑定仍有空缺且陪玩资格匹配的需求项，但不会按先后自动获胜；客户按候选池版本一次原子终选，全部有效席位填满后订单才进入 ACCEPTED，并为每位入选者生成关联需求项的陪玩明细和个人分成快照。
  • 每位陪玩独立绑定一个服务目录版本；同一订单内可同时存在技术陪玩、娱乐陪玩等不同项目。每条有效明细固化陪玩身份与展示名，以及游戏、服务类型、地区、计费单位、数量、目录单价、明细价格、分成类型/值、来源和预计收益，后续目录改名或调价不得追溯历史。
  • 客服可编辑每位陪玩的项目、数量与价格；Discord 客户下单按逐项目录价格创建草稿。订单总价由 API 对所有有效明细价格求和，客户端不得直接写总价。按比例时每人收益为该人价格乘固化基点并向下取整；固定收益规则按该参与项目的计费数量计算。
  • L1 仅能操作本人已认领客服任务的订单，L2 及以上可在服务端解析的 Guild 范围操作。新增、移除和改价都要求幂等键、订单版本、原因和审计。
  • 只要订单资金尚未最终捕获，即使已在服务中或待客户确认，仍可增删陪玩或改价。提价或新增时原子增加订单预留，余额不足整次失败；降价或移除时以追加预留事件释放差额。捕获后全部明细锁定。
  • 客户不再提交 readiness。订单首次从已接单进入服务中时，必须所有当前有效陪玩均已就绪。服务开始后新增陪玩不倒退订单状态，但该陪玩仍须确认就绪；任一有效陪玩未就绪时禁止最终捕获。
  • 客户确认完成前必须看到最新的逐人价格、分成来源和派生总价；确认时才原子捕获当前预留，并为每位有效陪玩分别创建收益事实。
  • 订单礼物请求提交一个或多个订单陪玩明细 ID，不设业务选择上限。API 去重、校验其仍属于该订单且有效，再推导真实接收人；独立礼物请求只提交一个同 Guild ACTIVE playerProfileId。两者均不接受任意 receiver user ID。
  • 礼物总额为固化礼物单价乘去重后接收人数。一次多选在同一事务内为每位接收人创建独立礼物事实并原子预留总额；任一人失效、余额不足或价格版本冲突时零写入。

M11 候选池选秀式派单补充合同

本节取代本文和 M9/M10 中所有“第一位接单者胜出”、逐名额即时接单、自动重复抢单、Discord 在线/手动可接单门禁及接单后才创建协调语音房的描述。

  • 订单提交并成功创建原 FundReservation 后保持 PENDING_DISPATCH；Bot 只提供“开始招募”，统一 API 为本轮固化开始时间但不接收等待分钟数、不生成截止时间或自动关闭任务。仅客户可点击“终止招募”，重复终止请求必须幂等。
  • 陪玩点击“报名选秀”只创建候选池报名，不创建 OrderParticipant、不固化收益、不捕获或增加预留。报名和进入选秀语音房均不占用活动订单槽位。陪玩可同时报名多个订单，并可在客户终止招募前撤回。
  • 报名必须绑定仍有空缺的 OrderRequirement。API 只依据内部已审批 ACTIVE、同 Guild 及游戏/服务/地区等资格标签判断报名资格；不以 Discord presence 或手动 AVAILABLE 状态作为报名资格，也不提供陪玩可接单状态设置。
  • 活动招募卡必须是单张消息，并按服务端稳定顺序将一至九个需求映射到 1️⃣ 至 9️⃣。消息 ID、频道 ID 与 emoji-to-requirement 映射必须持久化；新增 Reaction 表示报名，移除 Reaction 表示撤回。API 只接受可信 Discord 观测并自行解析映射、重验资格和幂等恢复已撤回报名，不信任客户端提交的 poolId 或 requirementId。公开 Reaction 身份在派单频道可见属于已接受边界；数据库仍是授权后的业务事实来源。
  • 新订单首次发布候选池招募时，Worker 必须先在派单频道幂等发送黑猫主题“正在派单”图片消息，再发送原有报名 Embed；图片是独立的展示消息，不改变单张活动报名卡、Reaction 映射或业务状态。仅订单客户真正取消整单并使订单进入 CANCELLED 时，Worker 才幂等追加同主题“本单流单”图片；“终止招募”进入 SELECTION 不属于取消，不得发送流单图。Outbox 重试、Worker 重启或同订单后续招募轮次均不得重复发布相同状态图。
  • 单轮需求超过九个时创建候选池必须零写入并返回可追踪错误；Worker 也必须防御性拒绝发布，不得拆卡、分页、截断或只支持固定四个。Bot 重启时须读取活动卡绑定并对账 Discord Reaction 用户与当前有效报名事实，重复观测幂等，暂时失败通过重试恢复而不直接写库。
  • 仅客户手动终止招募后，候选池进入 SELECTION。Worker 必须将派单频道原报名卡原位更新为招募已终止并移除报名组件；选秀阶段不设置业务超时，不自动选人、不自动扣款、不自动取消；进入阶段时必须通过幂等 Outbox 在客服频道通知订单、客户、候选人数及语音链接，客服 Role 可查看、连接和管理，但 Discord Role 不构成业务 API 授权。
  • 选秀语音房暂不设置人数上限。进入 SELECTION 后客户、本轮全部有效报名者及配置的客服 Role 可见并可进入；报名者不因进入语音房而获得订单参与者权限。
  • 客户通过私密、可分页的候选池投影选择一个或多个报名者。最终确认必须在一个版本化事务中锁定订单、候选池和所选陪玩，重新校验资格、需求剩余席位及陪玩活动订单冲突，随后创建正式 OrderParticipant、固化个人分成并占用活动订单槽位；任一所选人失效时整次零写入。
  • 陪玩可报名多个订单，但只能成为一个活动订单的正式参与者。正式入选后，其在其他未结束候选池中的报名原子失效，并通过 Outbox 移除其他选秀语音房权限。
  • 本轮确认时，Worker 创建或恢复仅客户、入选陪玩和客服可见的 service-{订单号} 正式服务房，先移动客户、再移动入选陪玩；voice_channel_id 指向正式服务房，selection_voice_channel_id 保留旧选秀房标识。未入选者状态改为 NOT_SELECTED，可看到本轮结束和最终入选公开昵称但不显示内部评分、排名或审核原因，同时撤销选秀房权限并移出。旧选秀房禁止重新连接，最后一人退出后自动删除；Discord 同步失败不得回滚业务选择，必须重试并在超过阈值后创建客服任务。
  • 部分席位入选后必须保留已选陪玩，只为剩余席位重新开放新一轮报名；不得回滚已选事实或创建第二笔订单预留。全部有效需求席位填满后订单才进入 ACCEPTED，随后仍要求所有正式陪玩 READY 才进入 IN_SERVICE。
  • 零人报名或客户对本轮候选均不满意时均不自动开启下一轮。客户可显式重新开始招募、取消并释放原预留或联系客服；重新招募必须携带被替换池及其版本，原子结束旧池、将仍有效报名记为未入选并创建可审计的新候选池轮次，且不得重复资金预留。
  • Discord presence 可保留为非授权的观测数据，但不得影响通知、报名、候选展示或最终选择。运营暂停、封禁、Guild 和服务资格仍由统一 API 的可信 Actor Context 与内部审批事实控制。

M12：轻量客服打卡、首响自动认领与态度评分

本节建立在 M10 多陪玩订单与 M11 候选池之上；客服事实仍归属于订单级 StaffTask，不绑定某个 OrderParticipant，也不改变订单资金、参与人或选秀语义。

  • 团队规模按不超过八人设计。L1/L2 可在 Dashboard 幂等上班和下班；打卡只记录班次，不成为查看、认领或 Discord 首响自动认领的权限门禁。L3/L4 不显示打卡动作。
  • 订单级 StaffTask 创建后固定在四分钟提醒、五分钟标记超时。超时只追加事实，不自动处罚，也不自动扣分、停岗、扣款或创建申诉流程。
  • 首响只接受订单频道内非 Bot、正文非空或含附件的 CREATED transcript 事件；认领按钮、内部备注、Bot 消息、空消息和编辑事件均不算首响。
  • 任何等级（L1–L4）的 ACTIVE 内部员工均可触发真实首响。员工首次真实回复时，API 在同一订单事务边界结束首响计时；订单没有负责人时自动认领最早创建的一条 OPEN 任务。
  • 已有 CLAIMED 或 PENDING_APPROVAL 负责人时不覆盖、不抢单。并发首响按订单串行化，最多产生一个自动认领结果，并记录 DISCORD_FIRST_RESPONSE 审计来源。
  • Dashboard 刷新后展示 API 中的自动认领结果；当前合同不承诺 WebSocket 实时推送。员工无需先打卡即可通过 Discord 真实首响认领。
  • 订单完成且存在真实客服首响时，客户可在二十四小时内提交一次一至五星客服体验评分。评分是独立写入，失败不得回滚订单完成、资金捕获或多位陪玩收益。
  • 一至二星必须选择固定原因：用语不当、态度冷淡、推诿责任、催促客户或其他；选择其他必须填写文字。评分不可编辑，不做积分、自动处罚、申诉或标签配置。
  • Dashboard 最近三十天只展示班次、处理数、超时数、评分数和平均分等简单事实；L1 仅本人，L2+ 按服务端 Guild scope 查看，不导出 transcript 正文、客户敏感信息或 CSV。

M13：业务集合稳定排序与可复用双视图

本节适用于 Dashboard 的订单、用户、陪玩、服务目录、服务套餐、礼物目录与礼物请求七类集合；展示模式不得改变统一 API 的对象 scope、脱敏、权限或业务动作。

  • 七类集合统一接受资源白名单内的 sortBy 与 sortDirection=asc|desc。默认使用 createdAt desc；禁止仅重排浏览器当前页，也禁止把客户端字段名直接拼入 SQL。
  • 订单支持创建时间、更新时间和金额；用户与陪玩支持创建时间、更新时间和显示名称；服务目录支持创建时间、游戏/服务名称、客户单价和版本；服务套餐支持创建时间、套餐名称、派生总价和版本；礼物目录支持创建时间、礼物名称、价格和版本；礼物请求支持创建时间、更新时间、金额和到期时间。
  • 所有排序必须追加唯一 ID 作为最终 tie-breaker，并对可空主排序值固定使用 NULLS LAST。名称 collation 由数据库合同统一冻结，不依赖浏览器 locale 或运行节点默认值。
  • HMAC 游标必须绑定资源、可信 Actor Guild、服务端 scope、筛选、sortBy、sortDirection、主排序值与唯一 ID。排序、方向或筛选变化后必须从第一页加载；旧查询游标返回 400 VALIDATION_ERROR，不得静默解释。
  • Dashboard 只提供 CARD 与 TABLE 两种集合视图。TABLE 在窄屏按同一显式列定义降级为行式列表；不建立第三套业务页面。
  • 两种视图消费同一 items、详情 API 和 item actions。切换视图不重新请求列表 API，不丢失筛选、排序、当前 items、分页或已打开详情，也不得改变字段脱敏和 action capability。
  • 筛选、排序、方向与视图写入可恢复的 URL query；游标不作为长期书签。非法 URL 值回退该资源默认值，并且不得发出非法 API 请求。
  • 集合工具栏、状态容器、卡片网格、显式列表格、窄屏列表和查询状态必须复用。表格列使用页面显式白名单，禁止从返回对象动态收集全部字段，避免列抖动及内部字段意外展示。
  • 首批不支持用户编排多列排序、状态字母排序、拖拽或隐藏列、保存多套个人视图、批量操作、导出、无限滚动或由客户端计算业务优先级。

M14：客服任务优先工作台与可行动订单上下文

本节只改善 M4、M12 与 M13 已有客服任务和订单事实的操作呈现，不改变 StaffTask、订单、资金、权限或 Guild scope 语义，也不新增 CRM。

  • 客服工作台必须让任务队列位于首屏操作区；本人已认领、已超时和待认领任务先于班次历史、三十天汇总及大型 KPI 展示。班次状态保留为紧凑控件，不遮挡当前任务。
  • 任务顺序由服务端生成任务优先级：先 OVERDUE，再按最早 responseDueAt 的 PENDING，其余按 createdAt 与唯一 ID 稳定排序。Dashboard 不自行推断业务优先级。
  • 每个可见任务返回 task-scoped 最小分诊摘要：订单公开编号、客户展示名、游戏/服务、金额、原因、等待起点和下一步动作。认领前只读预览不得授予完整订单详情或写权限。
  • Discord 深链只可由服务端基于可信 Guild 与频道 ID 生成。任一段缺失时链接返回空值、界面隐藏动作并说明不可用；不得生成 /channels// 或由浏览器拼接不完整 URL。
  • 任务卡必须优先显示客服可判断的对象、原因、已等待/剩余时间、当前负责人和下一动作；内部 UUID、原始枚举和 ISO 时间不作为主视觉标题。
  • Dashboard 指标必须可进入同一权限和 Guild scope 下的对应筛选结果，例如待处理、超时和进行中；指标跳转不建立新的 BI、导出或客户端聚合事实。
  • 订单列表与详情优先展示公开编号、客户/陪玩展示名、游戏/服务、中文状态、金额、相对时间及精确时间、当前阻塞和下一动作。内部 UUID、原因码、minor units 与审计元数据放入技术详情默认折叠区。
  • 高权限原始输入和理由码操作与日常客服摘要分区，并继续由既有 capability 控制。客户金额显示不改变 API 的 canonical CAT subunit 事实，所有写入仍走统一 API。
  • 真实员工 UAT 只覆盖当前业务 Guild，不要求准备第二个真实 Guild。跨 Guild 隔离仍是安全边界，并由 API、数据库与 fixture 自动化回归门禁证明。
  • P0 不新增 CRM、聊天记录归档、可配置 SLA、排班、复杂工作流、批量处理、实时推送或客户端业务规则。

M15：Dashboard 客服运营闭环

本节补齐员工已经可通过 Bot、Discord 或统一 API 完成但 Dashboard 尚无入口的运营动作。老板与陪玩的个人操作不迁入 Dashboard；Dashboard 不发送 Discord 消息。

  • 订单详情提供独立退款：L2+ 在合法捕获或可退款事实内选择金额、原因和证据，API 追加 Refund、消费与收益/返佣 Adjustment；不得把独立退款伪装成取消订单，也不得覆盖原资金事实。
  • 已认领任务的 L1 或同 Guild L2+ 可按订单读取订单频道 transcript 只读时间线，包括消息创建、编辑、删除、回复关系和附件元数据。读取不改变首响、任务负责人或订单；Dashboard 不发送 Discord 消息，也不提供编辑或删除。
  • L3/L4 在 Dashboard 管理 Bot 配置：频道、Role、业务时限、开关和播报模板必须经历服务端预检、版本校验、原因记录与审计；频道可执行受控测试投递。安全 Role 字段继续要求 L4 与近期 step-up。
  • L3+ 可从客户钱包选择可纠错的既有 WalletEntry，追加方向明确的钱包 Adjustment。客户端不得提交新余额；API 在同一钱包版本边界校验金额、引用流水、余额和幂等。
  • 员工控制的陪玩接单资格使用 PlayerReviewStatus=ACTIVE|PAUSED|SUSPENDED，最低 L3。PAUSED/SUSPENDED 不可看到或报名新候选池；恢复 ACTIVE 后按 Guild、标签和其他实时事实重新判断。陪玩端仍不提供在线或接单开关，legacy availability 与 Discord presence 不参与资格判断。
  • L2+ 可修改客户展示名，必须携带 expectedVersion、原因与说明；Discord 绑定、用户 ID、钱包事实、历史订单和只追加内部备注不可在该表单修改。
  • 员工账户管理：L4 权限页提供同 Guild 员工列表、待审批级别、有效级别、状态、权限版本和最近登录，并接入既有异人升权审批、降权/撤权与会话撤销。创建者或目标本人不得绕过异人复核，不能移除最后一个 bootstrap owner。
  • 所有动作继续由统一 API 解析 Dashboard session、Guild、有效权限与 permissions_version；Dashboard 不直连数据库、不计算资金、不信任客户端对象归属或角色。

M16：API 与 Dashboard 审查整改

本节冻结 main 分支代码审查发现的跨层一致性、错误恢复、请求竞态与工程门禁；不改变现行业务状态机、权限矩阵或 CAT 账本。

  • 除充值付款事实外，钱包、订单、礼物、消费、退款、收益、返佣、周报及结算默认显示 CAT。充值表单输入 USD cents、付款方式与 receipt，并按固定 1 USD cent = 1 CAT subunit 入账。
  • 陪玩结算同时展示应付 CAT 与线下实际支付 USD；CAT 是账本和结算来源事实，USD 是按固定关系生成的人工外部转账辅助值。两者必须带清晰单位，不新增可配置汇率或第二账本。
  • 钱包流水继续使用分页 envelope {items,nextCursor}。Dashboard 不依赖裸数组；API、OpenAPI、运行时 DTO 与测试 fixture 必须一致。
  • 所有生产注册路由必须存在于 OpenAPI。客服任务备注与升级分别使用 addStaffTaskNote 与 escalateStaffTask，继续执行本人认领 scope、权限、幂等与审计。
  • 统一写路由必须保证业务提交后幂等完成失败可恢复；不得让已成功业务长期停在 IN_PROGRESS 或过期后无条件重新执行。
  • targetId 与路径参数校验进入统一错误 envelope 和审计链；客户端输入错误返回受控 400，不得落入 Fastify 默认 500。
  • Dashboard 资源切换采用 latest-request 或取消机制，旧请求不得覆盖新客户；任何请求失败必须结束 busy/loading 并提供可重试反馈。
  • API 与 Dashboard 共享或生成 API DTO，禁止以双重断言掩盖 currency 或 envelope 漂移。CI 增加 lint 与 route-contract parity 门禁，新增代码不得继续复制分页、错误映射和请求状态基础设施。

M17：Bot 审查整改

本节冻结 main 分支 Bot 代码审查发现的频道副作用、启动就绪、Actor Context、HTTP 边界、工程门禁和模块职责问题；不改变订单状态机、资金语义、权限矩阵或 API 业务规则。

  • 私密订单频道必须由一个可测试适配器统一应用频道名称、权限覆盖、面板发送与置顶、既有频道返回、缺失频道恢复及失败清理；纯计划函数未接入运行时不得作为验收证据。
  • Bot 只能在环境校验、Discord 登录、统一 API health、关键 Guild 配置加载和常驻入口恢复完成后通过 readiness barrier。全量 Role reconciliation 应作为有并发上限的可恢复后台任务，不得让空配置期被误报为 Ready。
  • 所有 Discord 交互使用唯一 Actor Context builder；缺少 Guild 时在 Bot 适配层失败关闭，不得以空字符串或类型断言伪造可信 Guild Context。
  • Bot 内部统一使用 BotApiTransport 构造 Bearer、Actor、interaction 和幂等头，处理超时、网络失败、非 JSON 响应、错误 envelope 与 request ID。功能 client 不得重复实现这些边界。
  • Bot 必须纳入 lint、format、typecheck、build、专项测试与 Sapphire Piece discovery 门禁。格式化、纯移动和行为变更使用独立提交，新 warning 不得增长。
  • service-center.ts 按 API transport/client、feature action、message renderer 和 custom ID route 渐进拆分；Sapphire handler 只负责输入转换、acknowledgement、调用与回复，不复制业务或基础设施逻辑。
  • 测试必须覆盖真实 handler 行为和“组件—路由可达性”，验证 defer/reply/update 顺序、Actor 头、频道副作用、过期组件和恢复错误；仅检查源码字符串不能证明运行时完成。

M18：Discord 情绪化体验与信息层级

本节把 Discord 从“能用的业务表单”提升为具有黑猫陪玩店辨识度、情绪价值和清晰层级的服务体验。目标品牌与情绪体感达到参考店铺的 80–90%，默认设计基准约为 85%；但不得以装饰牺牲状态、金额、权限、隐私、幂等和错误确定性。

术语与业务边界

  • 所有用户可见的 Discord 标题、正文、按钮、频道名、语音房名、图片文字和错误提示禁止使用“选秀”；统一按语境使用“试音”“试音匹配”“试音房”“报名池”“当前报名”“确认陪玩”和“本轮未匹配”。
  • “重新选秀”改为“重新招募”或“重新试音匹配”，“候选陪玩”改为“报名陪玩”或“试音陪玩”。数据库枚举、API operationId、SelectionPool 等内部技术名称可继续保留，避免无业务收益的数据迁移。
  • 体验改造不改变订单状态机、资金语义、权限矩阵、Actor Context 或统一 API 业务规则；Bot 仍只展示 API 返回事实，不在文案或组件层推导报名资格、余额、下一状态或对象归属。

视觉密度标尺

  • 公共欢迎与导航：90。使用原创品牌横幅、分区导航、暖场文案、适量 emoji、可信服务承诺和真人客服入口，让新成员第一屏就感受到黑猫品牌。
  • 派单与关键里程碑：85。使用状态横幅、游戏主题图、结构化 Embed、轻量庆祝或安抚文案和明确操作提示，但同一消息不堆叠两张全宽图。
  • 订单私密主面板：70–80。在保证游戏、服务、数量、价格、老板需求、当前进度和唯一下一步可扫读的前提下，增加品牌标题、阶段性陪伴语和更清楚的视觉节奏。
  • 短暂私密反馈：45–55。报名、撤回、保存备注和普通成功提示保持紧凑，但允许一句有辨识度的黑猫回应；不为每次点击发送庆祝图。
  • 资金、权限与错误：20–35。金额、写入确定性、request_id、权限和恢复动作必须直白；禁止用花哨语气弱化风险。

统一消息构图与 Embed 层级

  • 高价值公共节点采用“横幅 → Embed → 按钮或 Reaction”的构图；单游戏派单使用对应游戏主题横幅，多游戏订单使用通用正在派单横幅，取消整单使用流单横幅。图像须为原创黑猫主题，不复制游戏官方 Logo、角色立绘或竞品素材。
  • Embed 固定阅读顺序为：标题 → 情绪化引导 → 核心事实 → 老板需求 → 当前进度 → 下一步 → 页脚。字段名使用单个语义 emoji；字段之间以空行、独立 field 或短分隔线形成稳定视觉节奏，禁止依赖连续多行纯文本挤在同一段。
  • 老板自由备注用引用样式或独立“老板需求”字段完整展示；不得与系统状态、报名名单或操作说明混排。空备注显示克制空态，不伪造需求。
  • 一个 Embed 只设置一个主动作语义；按钮颜色和顺序保持稳定。破坏性动作使用危险色并二次确认，状态刷新使用中性色，主要前进动作使用品牌色。
  • 报名、撤回、就绪和状态推进优先原位编辑同一消息；高频变化不得不断新增公共消息。编辑、重试和 Worker 重启沿用既有稳定业务键与 Outbox 幂等，不重复横幅、庆祝或提醒。
  • emoji 是路标而非填充物：标题最多一个主图标，字段各一个语义图标，正文每段通常不超过一个装饰 emoji；颜文字只用于低风险欢迎或庆祝，不进入资金、权限、失败和客服升级信息。
  • 颜色使用稳定语义：品牌紫蓝表示进行中，青绿表示成功，琥珀表示等待或需要注意，红色表示取消或失败，灰色表示历史或不可操作。不得仅依赖颜色表达状态。

流程覆盖与验收

  • 新人加入 Guild 后，Bot 自动发送一条品牌迎新私信；具服务器管理权限且经统一业务 API 校验具 welcome_dm.send 的 L2–L4 员工可使用 /welcome @玩家 重发同一消息。手动路径只读取专用的安全迎新上下文，不得借用 bot_config.read 或返回完整 Bot 配置。两条路径只做导航，不自动注册账户或改变业务状态；私信关闭时不得公开补发或泄露目标，只记录可诊断失败并在手动路径返回 ephemeral 提示。
  • 欢迎/导航、四步下单、订单主面板、派单、数字 Reaction 报名、试音匹配、全体有效陪玩就绪、服务中、完成、礼物、取消、客服求助及错误恢复均必须复用统一视觉/文案 token。
  • 欢迎、派单、试音匹配、服务开始、完成和真正取消属于可使用横幅的里程碑；普通选择、分页、刷新、报名撤回和表单校验只更新 Embed 或短暂私密反馈。
  • 自动化必须覆盖用户可见禁词、Embed 字段顺序、组件限制、横幅选择与消息幂等；真实 Guild UAT 需在桌面和手机宽度核对扫读性、图片裁切、按钮换行、Reaction 说明、mention 静默及客服/老板/陪玩三种视角。

M19：跨角色状态一致性与实时刷新

本节把状态变化视为客户、陪玩、客服 Discord 协同卡与客服工作台共同消费的业务事实，而不是只刷新触发操作的一方。本节与 M10 一并取代旧“客户与陪玩双方 readiness”描述：客户不提交 readiness，订单首次开始服务前必须所有当前有效陪玩均已就绪。

事实、投影与更新边界

  • 每个业务写入必须在统一 API 内完成状态、资金、审计与版本变更；事务提交与 Outbox 写入必须处于同一原子边界。Bot、Worker 和 Dashboard 只读取最新投影，不自行推导下一状态、余额、资格或权限。
  • 订单状态或相关事实变化后，必须核对客户订单面板、陪玩可见信息、客服协同卡、客服任务队列、客服订单详情及相关钱包/资金投影。没有对应内容的消费者可以不渲染，但不得因为不是操作发起者而遗漏更新。
  • Discord 高频变化必须原位更新已持久化消息；Outbox 重试、Worker 重启和重复事件按稳定业务键收敛。展示失败不回滚已提交业务，也不得再次执行资金或状态写入。
  • 客服工作台在自身写成功后立即失效并重取受影响查询；订单或任务详情在前台可见时短轮询，页面恢复可见时立即重取，并继续提供手动刷新。陈旧响应不得覆盖较新对象或版本。
  • 正常 Worker 下一轮应在目标五秒内收敛 Discord 投影；超过三十秒仍未收敛、Outbox 达最大重试、消息丢失或投影版本倒退时产生结构化告警，包含订单、事件、目标消费者和 request_id，但不记录敏感正文。

下单与服务生命周期

  • DRAFT 至 PENDING_DISPATCH 必须同步需求、老板备注、报价、预留和订单版本；开始招募、报名、撤回、终止招募、部分确认与重新招募必须同时收敛公开报名卡、客户面板和已有客服投影。
  • 进入 ACCEPTED 后，客户不显示 readiness 动作；客户面板、陪玩面板、客服协同卡和客服工作台均按统一 API 返回的有效参与人逐名显示 ✅/⏳、截止时间及全员状态。
  • 订单仍处于 ACCEPTED 时，任一陪玩确认或撤销就绪都必须原位更新客服协同卡，不能因为状态值未改变而跳过。readiness 超时只指出尚未确认的陪玩并创建唯一客服任务，不要求客户确认，不自动开始或捕获。
  • 仅 API 返回 IN_SERVICE 后，各端才显示实际开始时间；阵容、项目、价格或预留在捕获前调整后，客户、受影响陪玩和客服必须重取同一订单版本。
  • 申请完成、确认完成、取消辅助、真正取消和异常结案必须同步客户/陪玩动作、客服任务、资金事实与订单事件。只有 API 返回 COMPLETED 或 CANCELLED 才显示对应终态或一次性里程碑图片。

覆盖与验收

  • 详细消费者与恢复要求以 P0开发交付包/01-UIUX/跨角色状态刷新矩阵.md 为准，覆盖 DRAFT、PENDING_DISPATCH、ACCEPTED、IN_SERVICE、PENDING_CONFIRMATION、COMPLETED、CANCELLATION_ASSIST、CANCELLED 和 EXCEPTION。
  • 除订单外，礼物、客服任务、退款与 Adjustment、陪玩准入及 Bot 配置同样必须审计所有受影响消费者，不得只刷新客户或陪玩一侧。
  • 自动化必须覆盖业务与 Outbox 原子性、每个转换的消费者覆盖、Discord 原位更新与重启幂等、客服逐人 readiness、超时文案、Dashboard 主动重取及陈旧响应隔离；真实 Guild 以客户、陪玩、客服三种账号验证。

M20：Discord 动作清晰度与控件收敛

本节解决同一业务动作由多个 renderer 各自拼装所造成的按钮缺失、跨角色混放、标签含糊和布局拥挤。每个客户可操作的非终态订单都保留取消入口；可用动作必须来自统一 API 的可信事实。

可信动作与角色视图

  • 统一 API 为客户、当前陪玩和客服分别返回 availableActions；动作至少包含稳定 action key、是否可执行、目标角色、危险级别和不可执行原因。Bot、Worker 与 Dashboard 不得只凭状态或客户端自报角色推导动作。
  • 客户主面板只呈现老板动作，陪玩工作台只呈现本人可执行动作，客服协同卡只呈现客服动作。逐人就绪等共享事实可以只读复用，但陪玩写按钮不得出现在老板常驻卡上。
  • DRAFT、PENDING_DISPATCH、ACCEPTED、IN_SERVICE、PENDING_CONFIRMATION、CANCELLATION_ASSIST 和 EXCEPTION 均必须提供符合当前状态的取消入口；COMPLETED 与 CANCELLED 已是终态，不再显示取消。
  • 取消入口只发起 API 预览或写入：草稿和待派单可按合同直接取消；已接单、服务中、待确认和异常状态进入或复用客服审核。只有 API 返回 CANCELLED 才展示已取消、释放或退款结果。

首次使用可理解与布局

  • 按钮统一使用“动词 + 对象/结果”。例如“加入这个单点服务”“把此套餐加入订单”“核对订单与总价”“提交订单并预留猫条”“结束报名，进入试音”“陪玩：我已准备好”“老板：确认服务完成”和“刷新最新状态”；禁止脱离上下文的“进入”“查看”“确认”“刷新”。
  • 一屏最多一个 Primary，每行通常不超过三个按钮；主流程、导航/刷新/客服和危险动作分行，危险动作单独成行。无目标的禁用按钮和空分页控件应省略。
  • 分页必须同时支持上一页和下一页；候选确认页即使已有报名陪玩，也保留取消、刷新和客服入口；四步下单从第一步起始终保留取消。
  • 完整状态、角色、标签和布局合同以 P0开发交付包/01-UIUX/Discord动作与按钮矩阵.md 为准。自动化按状态 × 角色表驱动，并在真实 Guild 桌面与手机验证首次使用理解度和按钮换行。

M21：低负担完单评价与五星好评播报

本节以已完成的多陪玩订单为唯一评价来源，将旧的单一客服态度评分扩展为订单整体、陪玩与客服三类可选评价。礼物合同与运行时不在 M21 范围内。

评价对象、资格与不可变事实

  • 订单进入 COMPLETED 后二十四小时内，订单客户可评价订单整体、每位有效陪玩和本单实际客服；三类对象全部可选，未评价任何对象也不影响订单、资金、收益或后续下单。
  • 订单整体、每位有效陪玩和本单实际客服均由统一 API 根据可信 Actor Context、订单归属、Guild、完成事实、OrderParticipant 与真实客服首响推导。客户端只提交 API 返回的短期目标键，不接受任意陪玩、员工或 Discord 用户 ID。
  • 没有真实客服首响时不提供客服评价对象；多位陪玩逐人形成独立评价事实，允许只评价其中一人、多人同分或每人不同分。
  • 每个合法对象每单最多一条一至五星评价，星级点击成功即保存且不可编辑。留言始终可选，可在评分后追加一次且不得覆盖原评价；退出 Discord 流程不撤销已经保存的星级。
  • 评价与留言只追加、不得硬删除；失败或重复提交不能回滚订单完成、FundReservation 捕获、消费、逐人收益或返佣。评价不自动影响派单、准入、收益、权限、处罚或资金。

Discord 低点击流程

  • 完成订单面板只显示一个“评价本次服务”入口。打开后以 ephemeral 展示订单整体、未评价陪玩及符合条件的“猫舍前台”；已评价对象显示已保存星级，不要求重复操作。
  • 最快路径为打开评价中心后点击一次整体星级并离开。多陪玩订单可先多选一个或多个未评价对象，再点击一次共同星级；不同分数通过再次选择剩余对象完成。
  • 一至二星同样在点击成功后立即保存，不增加必选原因或其他前置步骤；P0 只提供可选留言。自由文本通过新 Modal 收集，最多五百字；Modal 内不做动态级联。
  • 分页、选择上下文和已保存事实来自 API 或签名消息状态，不依赖 Bot 进程内 Map；重启、旧组件或版本冲突只回读最新评价中心，不重放评分意图。

五星公开播报与隐私

  • 只有至少一条五星事实且老板在预览后明确同意公开，API 才创建一次性好评发布快照与 REVIEW_BROADCAST Outbox；保存五星本身不等于公开同意。
  • 每个订单最多发布一张聚合卡，按对象类型明确区分“订单整体五星”“陪玩五星”和“客服体验五星”，并可展示订单公开编号、游戏/服务名称、完成时间和阵容人数等安全基本信息。
  • 混合评价只公开快照中的五星对象；不得公开未评价对象，也不得公开一至四星、低分原因、自由留言、未获五星对象、客户身份、价格、钱包、订单私密备注、频道或内部客服身份。客服对外只显示“猫舍前台”。
  • 五星卡只投递到同 Guild 经 Bot 配置核验的 review_broadcast_channel_id 独立好评展示频道；未配置、频道不属于本 Guild 或 Bot 无发言权限时失败关闭，并允许发送配置验证消息。
  • 老板选择仅内部保存、关闭面板或未明确同意时零公开写入。播报失败只重试同一 Outbox 和消息，不重复评价、不重复发布，也不改变订单或资金事实。

M22：独立送礼入口与匿名模式

本节扩展现有礼物来源和展示边界；订单内送礼继续保留，资金预留、客服核对、分级审批、捕获与 Outbox 播报语义保持不变。

  • Bot 在同 Guild 配置的 gift_entry_channel_id 维护一条可恢复、可原位更新的常驻消息；老板点击后以 ephemeral 流程选择一位 API 返回的 ACTIVE 陪玩和一项有效礼物。
  • 独立入口只提交 playerProfileId、礼物版本和可选 anonymous；API 依据可信 Actor Context 重验 Guild、陪玩状态、Discord 绑定、礼物版本和余额，并推导真实 receiverId。客户端永远不能提交任意 receiverId。
  • 余额不足只展示差额、充值帮助、刷新余额和返回，不创建礼物、预留或客服任务；最终确认时仍在同一并发边界重新校验并原子预留。
  • 匿名只影响面向陪玩与公共频道的展示：展示名统一为“匿名老板”，不得包含发送者 mention、昵称、Discord ID、头像、订单号或私密频道信息。
  • 客服、资金、风控和审计仍使用真实 sender_id；匿名不是对内部授权、反欺诈、对账、争议处理或审计的隐藏机制。
  • 客服辅助采用模式 B并作为单独 Story 交付：具备专用 gift.assist 权限的客服，可从老板本人发送的客户授权消息打开 Discord 消息右键菜单“协助此老板送礼”。API 依据可信客服 Actor Context 和同 Guild Discord 绑定解析唯一余额所有者，客户端不得提交任意 senderId。
  • 客服选择陪玩、礼物和公开/匿名后，最终 Modal 必须同时提交必填原因与客服本人六位 TOTP。客服是最终确认人；TOTP 只验证客服本人，不冒充老板确认，也不保存或记录验证码明文。
  • 短期辅助 challenge 绑定客服、permissions_version、Guild、老板和客户授权消息的频道/消息 ID，十分钟过期、最多五次 TOTP 失败且只能消费一次。最终事务重新验证 challenge、权限、客户、陪玩、目录、价格和老板余额，并原子创建礼物、预留、客服任务与成功审计；未授权、错误、过期或重放均零业务写入。
  • 礼物发布门禁必须使用每次运行独立迁移和销毁的 PostgreSQL fixture，自动覆盖订单内、独立和客服辅助三条入口的资格、余额、TOTP、权限、并发、预留、捕获、释放、匿名投影和 Outbox 重试。数据库直写只用于准备前置事实，所有状态迁移仍经统一 API 或 Worker；非 UI 自动化不得代替 Desktop/Mobile、消息右键菜单、ephemeral 可见性和真实频道投递的外部 UAT。
