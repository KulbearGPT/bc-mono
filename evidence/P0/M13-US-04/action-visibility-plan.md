# M13 双视图操作入口修复计划

## 问题基线

- 范围：订单、用户、陪玩、服务目录、服务套餐、礼物目录、礼物请求七个共用集合页。
- 复现环境：L4 fixture，1280×720，CARD 默认视图。
- 现象：动作仍存在于 DOM 和权限模型中，但卡片把动作放在大块摘要、事实区之后。首条记录的动作顶边落在 765–873px，全部位于 720px 首屏之外，运营人员会认为“查看详情、编辑、删除、审批、取消”等入口已经消失。
- 测试缺口：既有组件测试只断言部分页面含有“查看详情”字符串；既有双视图验收没有约束记录动作在首屏内可发现，也没有逐页锁定 collection/item action 矩阵。

## 实施方案

1. 新增七页 CARD/TABLE 动作矩阵组件测试，覆盖集合级新建动作、详情入口和按状态/权限允许的记录动作。
2. 新增 1280×720 浏览器门禁，逐页确认首张卡片的可用操作区域在初始视口中可见，并确认切换 TABLE 后同一动作仍可达。
3. 提取共享 `CollectionItemActions` 渲染器，统一详情与记录动作的条件判断，避免卡片、桌面表格和窄屏行式列表各自漂移。
4. 将卡片动作从底部 footer 前移到标题之后，使用有名称的“可用操作”区域；footer 只保留时间或内部编号。保持服务端权限、状态适用条件、API 请求和资金语义不变。
5. 运行目标组件测试、目标 Chromium E2E、Dashboard 关联回归、typecheck、production build 和 diff 检查；为七个修改后的页面分别保存 CARD 与 TABLE 截图。
6. E2E harness 保留 3000/5173 默认值，同时允许通过环境变量选择隔离端口，避免新 worktree 验证中断原工作区的开发进程。

## 完成边界

- 本修复只解决 M13-US-04 中七类集合双视图的操作可达性回归，不新增业务动作，不扩大权限，不修改 API、数据模型或业务状态迁移。
- M13-US-04 原有的真实 L1–L4 员工、键盘人工签署及产品/运营/QA 签署门禁不因本地截图与自动化而被冒充完成。
